# 尽力关联的启发式忽视手头强信号: 猜测式外键挂错导致消费率漏计

## 背景 / 现象

观测面板头条 KPI"条目消费率"(consume_rate = 被返回后又真被 kb_get 读过的条目 ÷
被返回总数)靠 get 事件的 `trace_id` 关联回它属于哪次 search: `_consumed_ids` 要求
"get 所在 trace 的 returned 含该 id"才算消费。

get 事件的 trace_id 由 `latest_search_id(caller_repo)` 生成——取该 caller **最近一条
search** 的 id。第二十二轮探针实测序列 `search A(返回 k1,k2) → search B(返回 k3) →
kb_get(k1)`: k1 挂在 B 下, 而 B.returned=[k3] 不含 k1 → 消费集判空, consume_rate 从
真实的 0.33 掉到 **0.0**, 估算节省 token 同步归零。agent 真实工作流恰恰是"连着搜几
轮再回头读前面某条", 命中率高时反而漏得最多。

## 根因

外键关联用了**猜测式启发式**(取最近一条), 却忽视了手头就有的**强信号**:
`kb_get(id)` 的 id 参数——它几乎必然是从某次 search 的 returned 里抄来的。既然精确
匹配的判据(哪个 trace 的 returned 含这个 id)零成本可得, "最近一条"这种弱启发式
就成了纯粹的噪声源。

设计文档当初写了"尽力关联, 不追求强一致"为它背书——这句话**方向没错但被过度兑现**:
"尽力"应当是用尽所有可得信号后的兜底, 而不是"随便取一个近似值"。弱启发式 + 严格消费
判定(要求 returned 含该 id)的组合尤其致命: 关联与判定各用一套逻辑, 关联侧不看 id,
判定侧死盯 id, 两者错配的地方就是系统性漏计。

## 解决方案

`latest_search_id` 加 `entry_id` 形参, 两级策略: 先取"returned 含 entry_id 的最近一条
search"(精确匹配), 匹配不到才退回"最近一条 search"(保持原兜底语义, 覆盖外接源 id /
手动 get 等真关联断裂场景)。MCP kb_get 埋点传 `entry_id=id`; 外接源 id(source://…)
天然不在本地 returned 里, 自动走兜底, 无需特判。

设计文档同步修订那句"尽力关联": 明确"优先返回过该 id 的最近一条, 关联不上才退最近
一条"——避免下一个人再把强信号降级成猜最近。

## 验证

探针: 修复前 consume_rate=0.0 / saved_chars_est=0, 修复后 0.33 / 400(与手工核对一致)。
回归 test_trace.py(单元: 精确匹配优先 + 回退 + 不传参保旧语义)与 test_trace_mcp.py
(端到端: search 命中→search 零命中→get 首轮条目, 断言挂回首轮 trace), pytest
**304 全绿**。

## 适用边界与反例

适用于一切"事件/记录关联用启发式(最近/同用户/同会话)猜外键, 但被关联双方的数据里
其实带着可用于精确匹配的键"的场景: 埋点会话归并、日志 traceparent 重建、去重窗口
按时间近似代替按 key。**判据: 写"尽力关联/模糊匹配"注释前, 先确认更强信号是否真的
不可得**——若可得, 启发式只能是最后兜底, 不能当首选。

反例: 强信号确实不在手边时(如纯匿名浏览无会话 id), 时间窗启发式就是合理首选, 此时
应放宽消费判定(如同 caller + 时间邻近即算)而不是硬套精确匹配, 否则又漏计。关键在
"关联策略"与"判定策略"必须同源: 判定盯 id, 关联就必须用 id。
