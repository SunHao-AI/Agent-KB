# 懒启动子进程失败缓存永久短路误伤运行期进程死亡

## 背景 / 现象

观测面板蜘蛛回放桥(`serve.SpiderBridge`)懒启动 node 子进程, 设计意图是"缺 Node/克隆依赖时
记住错误不再重试(失败面收敛一次)"。第九轮走查实测: 桥成功工作后, 只要子进程**运行中途**
死亡(外部杀掉/自崩), 之后 serve 余生内所有回放请求立即失败, 面板全部降级 SVG 并显示
`桥不可用: [Errno 22] Invalid argument`——即使 node 环境与克隆仓完好、重启 serve 即恢复。

## 根因

`replay_url` 把两类完全不同的失败塞进同一个永久标志 `_dead`:

1. **配置性缺失**(spawn 前就缺 node/依赖): 永久短路合理, 重试也不会好;
2. **运行期进程死亡**: `_send` 向已关闭的 stdin 管道写入 → Windows 抛
   `[Errno 22] Invalid argument`(OSError)→ 被 except 标 `_dead` → 永久短路。

进程死亡是可恢复状态(下次请求重新 spawn 就能好), 却被当成配置缺失永久拉黑。次生问题:
`_urls` 会话缓存里的 previewUrl 指向死进程的端口, 死亡后仍会原样命中返回(iframe 白屏)。

## 解决方案

失败缓存只对"从未成功起过桥"生效: `_dead` 仅在 `_mcp is None` 时短路;
每次请求先 `p.poll()` 探活, 死桥 `close()`+置 `None` 后重 spawn, 同时清空指向死进程的
`_urls` 缓存。回归测试 `test_api_spider_revives_after_bridge_process_death`
(假桥 poll()=1 模拟死亡, 断言自动重生与旧缓存作废)。

## 验证

浏览器实测修复前后对照: 修复前杀桥→第二次起所有条目立即降级(Errno 22, 稳定复现);
修复后杀桥→点条目自动重连新桥(新 session/新端口, 无降级)。pytest 282 全绿。

## 适用边界与反例

适用于一切"懒启动 + 失败缓存"的子进程管理器(浏览器驱动、语言服务器、编译守护进程等)。
判据: **缓存错误前先问"重试一次会不会变好"**——spawn 前的依赖缺失不会, 运行期死亡会。
反例: 若进程死亡由资源耗尽等系统性原因导致, 无限重生会放大故障, 应配合重启上限/退避。
