# 指标消费方读生产方从未写入的事件字段且消化判定不分时间方向

## 背景 / 现象

观测面板"零命中周报"是驱动团队补库的反馈回路: 零命中 query 上榜, 若同 caller 后续
同词命中则标"已消化", 消化率 = 已解决/上榜。第十七轮走查实测两处让周报**系统性高估
消化率**的缺陷:

1. **时间方向性缺失**: 先命中、后来反而查不到的词(条目被降级/删除/改名), 仍被标
   已消化——待消化榜漏掉的恰是"曾经能用现在失效"、最该补的词;
2. **suggest 死分支**: 消化判定读命中事件的 `s.get("suggest")`, 但生产方
   `build_search_event` **从不往任何事件里写 suggest**(它只活在 report/MCP 返回值里,
   从未进 trace 事件)——该分支恒为 None, "按 suggest 改写后命中"这条 FR-3.2 设计的
   消化路径**从上线起就没生效过**。

## 根因

两者同根: **消费方按"文档设想的数据形状"而非"生产方实际写出的形状"写代码, 且判定
逻辑无时间语义**。

- 消费方 `zero_hit_board` 从 docstring/设计意图出发认为"命中事件带 suggest"(字段注释
  也这么写), 但两边从未对过真实事件样本; `dict.get` 的宽容让死分支静默存在——如果
  当初写成 `s["suggest"]` 早就 KeyError 暴露了。**`.get` 在跨模块契约处是掩盖断链的
  消音器**。
- 消化判定用"全量预扫所有命中事件建词表"——O(n) 一把梭省事, 但"已消化"本质是时序
  命题(失败**之后**解决了才算), 集合语义丢失方向后不可恢复。
- 衍生坑: 同词多 caller 聚合时, OR 合并会把 a 的消化误盖到 b 的未解决上, 必须 AND
  (任一 caller 现状未解决就该留榜)。

## 解决方案

- **生产方补契约**: `build_search_event` 在 `returned` 为空时把 report 里的 suggest
  透传进事件(`ev["suggest"]`)——建议词挂在**失败事件**上才符合语义(它描述的是"这次
  失败时系统建议了什么");
- **消费方时间感知**: 命中事件按 `(caller, ts, tokens)` 留存, 对每次失败只认
  `hts >= ts` 的命中; 消化状态跨 caller 用 AND 聚合;
- **契约测试**: 三个回归分别锁"先命中后失败必回榜""suggest 经失败事件生效""多 caller
  AND 语义", 事件构造用 `_search` helper 与真实 schema 对齐。

## 验证

探针(修复前): `css slash` 先命中后失败仍 `digested=True`; `build_search_event` 输出
字段列表中无 `suggest`(死分支实锤)。修复后同探针: 方向性正确、suggest 在场且消化判定
生效。回归 `test_zero_hit_board_digestion_is_time_directional` /
`test_zero_hit_board_suggest_on_failure_event_is_live_path` /
`test_zero_hit_board_multi_caller_requires_all_resolved` 通过, pytest 296 全绿。

## 适用边界与反例

适用于任何"生产/消费分离的事件流 + 指标消费方"场景: 消费方读到的字段必须能在生产方
代码里找到写入点——**跨模块用 `.get` 读对方字段前应 grep 生产方确认写入存在**, 死分支
比 KeyError 危险得多(它默默给出错误的"正常"数字)。时间性判定(已解决/已恢复/已消化/
首次/末次)不能用"全量集合成员"近似, 必须显式比较事件时间。反例: 若指标本就定义在
无序集合上(如"总命中次数"), 全量预扫是正确的, 勿过度加时序化。

## 新发现(第二十轮, §38): 同一模式的"机制整体空转"变体 + 存量修复缺口

`review_by`(时效到期日)在本仓是**同一模式的更彻底实例**: spec 属性表写明"到期进入
待复核清单"、front-matter 示例给了 `review_by: 2027-10-12`、消费链四件套齐全
(taxonomy schema → `query.due_review` → `stat.due_review` → `kb stat --due-review` +
AGENTS.md 工作流)——但 `create_entry`/`gate.review` **没有任何代码写过这个字段**。
探针实测: 走完 draft→accepted(verified) 全流程, fm 无 review_by; `due_review` 放到
2030 年仍空。待复核机制**自上线起空转**, `kb stat` 的"待复核数"恒 0(= 永远健康的
假阴性)。

与 suggest 死分支的差异在**症状形态**: 那边是消化率高估(错数字), 这边是功能整条
静默失效(恒空=永不告警)。**恒空的指标比错指标更难发现**——错数字偶尔还扎眼,
"0 条待复核"看起来就像"知识库很健康"。检测法同条: 消费方读字段前 grep 生产方
写入点, 写入点为零 = 机制不存在。

修复时的**第二层坑(本条新增维度)**: 补上生产链(accepted 落 `review_by=accepted日+
周期`)只修**增量**——存量 accepted 条目仍无此字段。且本仓状态机禁
`accepted→proposed/accepted`(终态化设计), 存量条目**没有任何合法路径**再获得该字段。
故消费侧必须兜底: accepted 无 review_by 时按 `updated + 周期`计算到期日, 让历史条目
自然纳管。通用判据: **给"新数据才有"的字段补生产链时, 同步问一句存量怎么办**——
要么幂等回填脚本, 要么消费侧兜底推导, 二选一, 缺了就是"修复只对明天生效"。
