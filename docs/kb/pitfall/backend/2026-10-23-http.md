# HTTP 服务端出错路径不回读请求体就关闭连接, 把已写出的错误响应吞成连接重置

## 背景 / 现象

`kb serve` 的 `POST /api/ingest` 鉴权失败应回 401, 测试客户端
(`urllib.request`)偶发拿到的是 `ConnectionResetError: [WinError 10054]`
而不是 401——全量 pytest 套件里 `test_ingest_append_dedup_and_redlines`
约 1/8 概率失败, 单跑必过, 长期被当作环境 flaky 登记"暂不修"。

## 根因

HTTP 客户端(`http.client`)发送带体请求是**两次 write**: 先 headers, 再 body。
服务端 `do_POST` 的旧顺序是"鉴权失败 → 直接回 401 → 连接关闭", 全程没碰
`rfile` 里的请求体。当 body 段恰好在服务端 close 之后才到达(套件负载高、
调度延迟拉开两段间隔时概率上升), 内核发现数据落在已关闭的 socket 上, 按
TCP 语义**回 RST**——RST 会丢弃接收方向上已排队但客户端尚未读走的 401 响应
字节, 客户端只见连接重置。Windows 上表现为 10054(对端)/10053(本端), 且
1.0 响应无 keep-alive 复用, 每次请求都重新掷骰子。RFC 9110 §10.1.4 明确要求:
处理带体请求中途出错时, 服务端应先读完(drain)或可靠关闭前读取请求体。

## 解决方案

把"解析 Content-Length + 回读 body"提到**所有错误返回之前**(404/401/400 统一
先 drain 再回响应), 上限与合法路径同为 64KB, 超限不读直接置
`close_connection`(防读放大):

```python
raw = b""
if 0 < n <= 64 * 1024:
    raw = self.rfile.read(n)
elif n > 64 * 1024:
    self.close_connection = True
```

## 验证

受控时序探针(原始 socket 先发头、睡 0.4s、再发体): 修复前读响应必炸
`ConnectionAbortedError(10053)`, 修复后稳定读到 `HTTP/1.0 401`。回归测试
`test_ingest_401_drains_body_so_response_survives` 用同构造固化(git stash
回退源码后该测试即失败, 对旧代码敏感)。修复后 `test_stats_serve.py` 连跑
8 次 0 失败(修复前同探针 1/8)。

## 适用边界与反例

- 任何"先校验后读体"的裸 HTTP 服务端都适用(stdwsgiref/BaseHTTPRequestHandler/
  手写 accept 循环); 框架型服务器(nginx/uvicorn)已内置 drain, 无需照搬。
- 请求体可能极大时不能无脑 drain——先读 Content-Length, 超上限直接关连接,
  否则错误路径变成内存放大攻击面。
- 反向陷阱: 若客户端在等服务端读完体才发下一段(100-continue 语义), drain 不
  会破坏它——这里 drain 的只是已声明 Content-Length 的普通请求。
