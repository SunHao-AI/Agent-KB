# 实体有两个唯一键, 去重只保了一个: 路径加了 -2, id 静默撞车

## 背景 / 现象

`kb new` 生成的条目有**两个唯一性约束**: 文件路径(`kb/<type>/<domain>/<slug>.md`)
与 front-matter `id`(`kb-YYYYMMDD-` + 4 位随机 hex)。第三十轮走查探针实锤:
创建函数对路径写了完整的 `while path.exists(): -2/-3…` 去重循环, 对 id 却
**一个校验都没有**——`secrets.token_hex(2)` 抽到什么直接落盘。撞上后两条条目
id 相同、路径被 `-2` 掩盖得"看起来很正常", 写入瞬间零信号; 恶果延迟爆发:
按 id 定位文件的 `_find` 只命中第一个, 另一条 `kb show / review / related /
export` 永久断链, 直到某次 lint 或人工翻仓才追溯。4 hex 空间只有 65536,
同日创建 N 条按生日悖论 N=100 即约 7.6% 概率撞车——多 agent 并发沉淀的繁忙
知识仓完全踩得中。

## 根因

两个缺陷叠在一处:

1. **"唯一性"在实现者心智里等于"文件名不冲突"**。路径去重循环是当初为中文
   标题同名(kebab 为空)加的, 加的人没意识到实体还有第二个键; id 字段生成
   与路径生成分居两个函数(`new_id` / `_unique_path`), 视觉上也暗示"各有各的
   事"。实际上 `id 不可变、slug 可改` 的契约(**id 才是权威主键**)恰恰说明
   被去重保护错了对象——被保护的是那个可变、可派生的次键。
2. **概率分配被当成确定性分配**。`token_hex` 是抽样不是发号: 小空间(4 hex)
   + 无校验, 等于把主键唯一性外包给了运气, 且失败模式是静默的。既有测试
   恰好每次只建一两条, 从未触发生日悖论区间。

修复过程中的二次教训: 首版"同日已占用 id 集合"按**文件名前缀**过滤同日文件
(省解析), 立即被自己推翻——slug 允许人工改名而 id 不可变, 文件名是 id 日期
段的**代理指标**, 代理会与事实源脱钩(§42 同族)。改为按 id 内容筛: `new` 是
低频动作, 全量解析换正确性完全划算。

## 解决方案

- `create_entry` 的 id 改走 `_unique_id`: 先收集仓内同日已占用 id 集合(按
  front-matter **id 内容**筛, 不信文件名), 生成后撞了就换下一个随机值重试,
  连续 64 次撞车才抛 RuntimeError(等价于同日条目逼近 65536 上限, 那本身就是
  异常批量写入信号)。
- 撞车从"静默双写"变成"创建当场失败": 与写入类数据一致性通则对齐——
  **约束必须在写入点强制, 且失败必须响**。lint 的事后 `duplicate id` 检查
  保留作兜底, 但绝不能是主防线。
- 回归: 恒同值随机源下第二条必须抛错 / 改名过的同日条目仍在占用集合内
  (test_new.py +2), 既有中文标题去重测试并入"同日两条 id 必须不同"断言。

## 验证

探针修复前后对账: 修复前 mock 恒同值随机源, 两条同日条目静默双写同 id、
`_find` 歧义命中; 修复后第二条 RuntimeError、真实随机连建 30 条 id 全唯一、
改名条目仍被占用集合捕获。pytest **323 全绿**(321+2 新函数, 另 1 处断言并入
既有测试), ruff `--select F,E9` 通过, `kb lint` 0 错。

## 适用边界与反例

适用于一切"实体有 ≥2 个唯一键 + 其一由随机/派生值分配"的创建路径(文件库
id、缓存键、短链码、会议号)。判据:**逐个唯一键问一遍"写入点谁在强制它?"**
——只要某个键的唯一性靠"概率上不会撞"或"事后检查才发现", 就是缺陷。缓解
优先级: 加宽键(4→8 hex, 生日悖论拐点从百级推到万级)可以降概率, 但**不能
替代写入点校验**; 反例: 键空间足够大(如 uuid4)且撞车后果可自动恢复时,
可以省掉读占用集合的开销——前提仍是"撞了会响"(唯一约束报错), 而非静默。

## 新发现(第三十六轮 §54: 同一主键判据的跨仓形态——export 只查路径不查 id)

`kb export` 把项目条目搬进共享库(破坏性: 写完目标即删源)。它的冲突检查只有
`dst.exists()`——而 dst 路径由 `type/domain/slug` 派生, **slug 可人工改、id
不可变**, 于是"目标仓已有同 id 条目(早前从别的项目上提过, slug 不同)"完全
绕过检查: 搬入后目标仓同 id 双条目, `_find` 只命中一个, 另一条 show/review
永久断链; 等 lint 报 duplicate id 时源已删, **两仓都回不去**。

这是本条判据的第二维: 不止"实体多键只保一个"要普查, **同一主键的每一个
写入路径**都要各自问一遍"谁在强制它"——本仓 new 修了(D-35), 跨仓 export 还
裸奔; 而且 export 用了"路径存在性"这个**派生投影**冒充主键检查, 投影相同
(id 同)不代表原像相同, 投影不同(slug 异)更不代表原像不同。跨仓场景还没有
现成的占用集合可查, 必须显式遍历目标仓条目按 id 比对(iter_entry_paths 唯一
事实源顺带覆盖)。

判据补全: **主键校验必须发生在每一个能让该键进入存储库的路径上(新建/导入/
合并/跨仓搬移), 且校验对象是主键本身, 不是它的任何派生投影**; 破坏性写入
(先删后写/搬移)的校验必须在删之前, 且拒收路径不得留下半状态。
