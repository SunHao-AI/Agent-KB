# 窗口起日取 UTC 日与全库本地日粒度基准混用(凌晨窗口多圈一天)

## 背景 / 现象

观测面板"7天/30天"窗口按钮把起日算成 `sinceDate(days)`: `new Date(Date.now()-days*864e5)`
再 `.toISOString().slice(0,10)`。后端 `_within` 用 `str(ev["ts"])[:10]` 与这个 `since`
做**字符串日期比较**。第十九轮走查在页面上下文模拟上海时间凌晨 02:00 复现: 用户点"7天",
后端拿到的起日是 `2026-10-15`, 而按数据自身日粒度应为 `2026-10-16`——窗口悄悄多圈了一天,
"近 7 天"实际显示 8 天的事件。白天点同一个按钮则完全正常, 所以缺陷每天只在
00:00–07:59(+08 区)出现, 白天做的走查/自测一律看不见。

## 根因

`toISOString()` 先把时间换算到 **UTC 再取日期**, 而本仓其余所有日粒度一律是
**本机本地日**: ts 由 `datetime.now().astimezone().isoformat()` 写入(带 `+08:00` 偏移,
`ts[:10]` 即本地日), stale 判定用 `dt.date.today()`(服务器本地日), CLI `--since`
默认 `_dt.date.today()-7d`(本地日)。UTC 日与 +08 本地日相差一天(本地钟点 < 08:00 时),
于是"每天有一段固定时间窗口偏宽一天"。

本质不是"前端算错了", 而是**同一批日期串在系统里有两个不可区分的基准**:
`2026-10-16` 既可能是 UTC 日也可能是本地日, 字符串比较无法察觉。日粒度比较只要基准混用,
错就是**按天规律性发作、且与走查时刻强相关**——白天测不出来, 不代表不存在。

## 解决方案

前端起日改用本地 getter 取值, 与 ts/stale/CLI 同基准:

```javascript
return `${d.getFullYear()}-${String(d.getMonth()+1).padStart(2,'0')}-${String(d.getDate()).padStart(2,'0')}`;
```

更根本的做法是**让日期基准显式化**: 后端窗口参数只接受 `YYYY-MM-DD` 并明确其含义是
"写入机本地日", 前端不要自己算日期而由后端下发起日; 或彻底改用时间戳 + 显式 tz 比较,
不再拿日粒度字符串跨端传。

## 验证

浏览器 E2E(页面上下文)以注入参考时刻 `2026-10-23T02:00+08`(而非改系统钟)复算起日:
旧算法 `sinceDate(7)` → `2026-10-15`, 本地基准应为 `2026-10-16`, `mismatch: true`;
新算法(本地 getter)同一时刻 → `2026-10-16`。非凌晨时段(实测当下真实调用页面
`sinceDate(7)`)新旧同返回 `2026-10-15`, 与"白天看不见"的现象判断一致。时刻序四处修复后
回归 `test_timestamp_order_is_offset_aware` / `test_stale_flag_is_offset_invariant`,
pytest **298 全绿**(既有测试全用同偏移 ts, 故旧实现也能过——正是"单机测不出"的镜像)。

## 适用边界与反例

适用于任何"前端算日期 + 后端字符串日粒度比较"的组合。判据: grep 所有 `toISOString`
出现在"算日期"而非"传输时间戳"的地方——`toISOString()` 用于**传时刻**没问题,
用于**切日期**就必须先确认对端基准。

**本条未彻底解决的问题**(诚实记录, 属面板既有设计): 整块面板刻意"以写入机时区为准,
不做本地化换算"(见 `fmtTs` 注释)。因此查看者若在与写入机**不同时区**的机器上看面板,
用查看者本地日算 `since` 仍会偏(偏差不止一天)。本次修复只消除了"同时区下每天
8 小时必现"的固定偏差; 真正的解法是窗口起日由后端(数据属地)下发, 前端不再自算。

反例: 存 UTC 时间戳(`...Z`)的库, `toISOString().slice(0,10)` 反而是正确基准——
判据始终是"跟数据自身的日粒度对齐", 不是"永远别用 toISOString"。

## 新发现(第十九轮补充, §37): 同一混用还发生在**时刻序**上, 且更隐蔽

同一条 ts 串(`2026-10-22T09:00:00+08:00`)除了被 `[:10]` 切日, 还被**当字符串直接比较**
来判断"谁更晚"。字符串序**只在全体同偏移时**才等于时刻序: 上海 `09:00+08:00`(=01:00Z)
与纽约 `08:00-05:00`(=13:00Z) 字符串判上海晚, 真实纽约晚 12h。单机自测永远绿(全员同偏移),
团队态联邦成员跨时区上报即同时错四处:

| 现场 | 后果 |
| --- | --- |
| `feed_events` 排序 | 实时流"最新"不是最新, 且 `limit` 截断会**丢掉真正最新的事件** |
| `aggregate.by_caller.last_ts` / `callers` 行集 `max` | "最近活跃"取错, 掉线检测(14d)基准失真 |
| `zero_hit_board` 的 `hts >= ts` | 消化方向判反: 跨时区的"失败后补库命中"被判未消化, 反向亦可能误判已消化 |
| `_ext_health_latest` 排序 | 外接源健康取到过期一次的状态 |

修复: 采集层提供唯一比较键 `trace.ts_key`(解析 ISO → 归一 UTC 秒; 无偏移按写入机时区
理解, 与 `_now` 的 `astimezone()` 一致; 解析失败退回原文保证键可比), 四处比较全走它;
**显示仍用原始串**(面板刻意以写入机钟点为准)。`stale` 的"距今"另改 `stats._age_days`
时刻差, 不再用"查看机本地日 − 写入机本地日"(两基准 + 日粒度取整, 14d 门槛附近抖一天)。

判据: grep `sort.*ts` / `max(.*ts` / `ts >=`, 凡对**带偏移的时刻串**做顺序比较都必须先归一。
`[:10]` 取日属于同一族: 先问"这个日属于谁的日", 再问"能不能直接比"。

## 与"固定基准渲染"条目的区别(勿混用两个结论)

`kb-20261013-27e3`(epoch 渲染成日历日必须固定 Asia/Shanghai)与本轮结论方向**相反**,
因为要解的问题不同: 那条是**展示**绝对时刻给不同时区的查看者 → 必须钉死一个基准时区,
否则同一份数据在不同机器显示不同日; 本轮是**窗口起日/比较**必须与**数据自身的日粒度
基准**对齐(本仓数据是写入机本地日), 以及对**时刻**比较归一时区。共同上位规则是:
**先确定"这个日/这次比较以谁的钟为基准", 再让所有环节显式用同一个基准**——
而不是"永远用 UTC"或"永远用本地"。
