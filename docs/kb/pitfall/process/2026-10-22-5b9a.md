# 重构复用写路径时语义漂移: 建议型命令变成终审执行手

## 背景 / 现象

`kb promote <id> --to stack` 在四处文档里口径完全一致——AGENTS.md 红线2"只做**建议**,
由人 `set-scope`/`kb export` 落地"、README §4"标记建议, 由人确认后迁移"、spec §9 终审
工作流(promote 出建议表 → 用户批次认定 → set-scope/export 执行)、测试设定 C12"加
needs-scope-review 建议, **不改 scope**"。

第二十一轮走查探针实测: 实际实现把 scope **立即改成 stack** 并把 `needs-scope-review`
标签**清除**。两个运行时后果: ① 刚发出的建议从 `kb stat --needs-scope` 人工待办清单里
消失(清单按该标签过滤)——建议即终审, 人工确认环节被整体架空; ② scope 与物理位置错位
(条目标着 stack 却躺在项目仓 `docs/kb/`), 双层检索按 scope 过滤时错层。

## 根因

git 考古定位到漂移引入点: `04e3414` 初版 promote 只加 promoted 标签(符合契约);
`480cd0e` "promote reuses gate.set_scope write path instead of raw scope assignment"
——初衷是好的(复用公共写路径获得枚举校验+标签清理+落盘一致性), 但把"复用 set_scope"
理解成"promote 就是 set_scope + 打个标签", **顺带继承了 set_scope 的终审语义**(改
scope + 清 needs-scope-review)。

本质: **重构时按"代码怎么复用"对齐, 没按"命令对外承诺什么"对齐**。set_scope 是终审
执行手(改 scope 是它的本职), promote 是建议标记器(改 scope 是它的违禁动作)——两者共享
写路径时, 建议型命令必须**剥离**执行型命令的副作用, 而不是继承全套。

更隐蔽的是 `480cd0e` 同时**新增**了 `assert fm["scope"] == "stack"` 的测试——错误行为
被测试当场固化, 此后任何 CI 绿灯都在为漂移背书。这类"测试跟着坏实现改"的提交, 比没
测试更危险: 它让下一个怀疑的人看到"这是设计如此"。

## 解决方案

promote 回归纯建议语义, 三态分离:

- **promote(建议)**: 只打标签——`promoted` + `promote-to:<scope>`(建议目标留痕) +
  `needs-scope-review`(进入/留在人工待办清单); **不碰 scope**。重复 promote 视为改判,
  旧 `promote-to:*` 替换不堆积。
- **set_scope / export_entry(终审落地)**: 人工决定后改 scope, 并经 `_strip_promote_tags`
  清掉**全部**建议期标签(needs-scope-review / promoted / promote-to:*——旧实现只清前者,
  promote-to 会永久残留)。
- 建议目标用 tags 承载而非新 front-matter 字段: tags 是 schema 自由数组, 不动派生
  schema(有测试锁 committed == derived)。

## 验证

探针对照(修复前/后同一脚本): 修复后 scope 保持 `project`、tags 为
`[needs-scope-review, promote-to:stack, promoted]`、`--needs-scope` 清单保留该条目。
回归 `tests/test_promote.py` 重写为 7 测试(建议不改 scope / 留在待办清单 / 改判目标
不堆积 / 落地清全部建议标签 / 非法与 project 目标拒绝 / 不改 status), pytest
**302 全绿**。

## 适用边界与反例

适用于一切"建议型 API 与执行型 API 共享底层写路径"的重构(review→改状态、标记→打标
这类近义对): 复用公共函数时逐项问"源函数的每个副作用, 目标命令的对外契约允许吗"——
枚举校验可以要, 状态变更必须拒。判据: 契约文档(AGENTS/README/spec)与测试断言冲突时,
先 git 考古哪个是原契约、错误行为是否被测试固化, 再决定改哪边。

反例: 若产品演进**有意**让 promote 直接生效(决策记录可查), 那应同步改契约文档并让
文档与实现一起翻——本例无任何此类记录, 四处文档一致站在"建议"一边, 故是实现漂移。
另注意与 `kb-20261022-648d`/`d8fb`(查重池/路径伪装)不同族: 那两条是"消费面看不见",
本条是"执行面做多了"——权限扩权与权限缺位同为契约破坏, 方向相反。
