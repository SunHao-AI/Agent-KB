# 查重池只比已发布索引看不见草稿致重复沉淀双双通过

## 背景 / 现象

沉淀门控红线 3 要求"沉淀前必须查重, 命中既有条目则更新不新建", 落地在 `create_draft`
(MCP `kb_create` 的实际逻辑): 查重命中抛 `DuplicateCandidate` 拒建。第十六轮走查端到端
实测: **同一条知识(同 body + 同标题)连调三次 `kb_create`, 三次全部成功建出三条 draft**,
中间夹一次 `kb index` 也拦不住。两个 Agent 并发沉淀同一踩坑, 各自都以为"库里没有才新建",
结果库里躺着 N 条重复草稿。

## 根因

查重池的可见性范围与写入目标**错配**:
- `_dup_hits` 只扫 `_index_records`, 而它读的是 `kb/index.jsonl`(**live 索引**, 只含
  accepted/proposed 等已过审条目);
- 但 `kb_create` 产出的全是 `status=draft`, 且 draft **不进 live 索引**(进的是
  `index.draft.jsonl`, 且不进检索索引)。
于是查重池**永远看不见任何 draft**——不管 `kb index` 重没重建都一样(rebuild 只是把
draft 写进 draft 索引, live 池仍没有)。再叠一层时序: 刚 `kb new` 出的 draft 连 draft
索引都还没重建, 连"扫 draft 索引"这条路都有窗口。后果还被**放大成不可自愈**: 这些重复
draft 不进检索索引, 后续 `kb search` / `search --status draft` 都看不见它们, 人工也无法
靠检索发现去重。

## 解决方案

查重池在 live 之外**并入 draft 候选**, 且 draft 侧**扫源文件现算指纹**而非读 draft 索引:

```python
for r in _index_records(rp) + _draft_records(rp):
    ...   # 指纹相等 或 标题 token 命中(phrases≥1 / weak≥2) 即判重
```

- `_draft_records` 遍历 `kb/**/*.md`, 取 `status==draft` 的条目, 用 `fingerprint(e)`
  现算 `dedup_key`。draft 池天然小(低频 + 单会话自审上限), 现算成本可忽略, 换来**无索引
  重建时序窗口**(刚 kb new 立刻可被下一条查重命中)。
- live 池不变(大, 用 index 里预算好的 `dedup_key`, 且 live 由人工/定时 index 维护恒有效)。

## 验证

- 端到端探针: 同 body 同标题连建三次——修复前三条全建成(backend 下 3 个文件), 修复后
  第二次即被 `DuplicateCandidate` 拦下(仅剩 1 条), 且中间 `kb index` 与否都拦得住;
- 回归 `test_create_dedup_against_existing_draft`(第二次建返回 `duplicate` 且含首条 id);
- **副作用即证据**: `test_review_session_cap_three` 原本用"Redis 池耗尽 独立验证0..9"造
  4 条 draft, 修复后第 2 条起就被正确判重(共用 ≥3 字中文词组"池耗尽")——该测试把"主体
  相同、靠序号区分"的取巧标题当作独立条目, 恰恰是被修复戳穿的旧依赖, 改标题为真正独立
  主题后通过。pytest 293 全绿。

## 适用边界与反例

适用于一切"查重集合 ⊂ 可写入集合"的系统: 若新写入先进一个隔离区(草稿/待审/暂存表)
而查重只比已发布区, 则并发写同一实体会绕过唯一性。判据: **查重必须覆盖所有已存在的
候选, 包括尚未晋升的**。当草稿区小且低频时直接扫源现算指纹最稳(无索引依赖); 草稿区大
时才考虑"写时同步维护一份查重索引", 但要接受重建时序窗口。反例: 若查重目标(如全局唯一
URL slug)有独立强约束层(数据库唯一索引)兜底, 应用层查重可只作友好提示; 但本场景的
"语义相似判重"(标题 token/正文指纹)本质无法用唯一索引表达, 必须在应用层做全。
