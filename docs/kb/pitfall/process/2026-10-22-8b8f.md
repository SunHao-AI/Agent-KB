# 同一概念两套发现规则: 质量门控与消费链各扫各的, 漂移出免检角落

## 背景 / 现象

kb 工具链里"哪些文件算知识条目"这一概念被实现了 **6 次、两种语义**:
lint 用"kb 根第一层目录再向下、排除点开头目录"(注释写明为避免扫入挂载子仓),
index/gate/query 用 `kb.rglob("*.md")` 全量扫。第二十四轮探针构造 kb 根直下散文件
`kb/loose.md`(front-matter 故意写坏: 非法 type、非法 status、缺 severity)——
**index.jsonl 收录它、可被检索命中消费, lint 却零报错**。同一份数据, 门控与消费链
看见的集合不同, 交集之外的部分就是"进检索但免检"的角落: schema 校验、重复 id、
指纹冲突、占位段检测全部绕过。

## 根因

"条目发现规则"是一个**跨模块共享概念**, 却没有唯一实现——每个调用点就近手写一遍
遍历。两种语义谁都没错(lint 排除点目录是为了不扫挂载外仓, 有其道理), 错在没有
把正确规则收敛成一个函数: 后来者在消费链上任选 rglob 复制粘贴, 与门控侧的窄规则
静默漂移。这是历轮"同概念多实现"家族(§38 恒空指标、§40 猜测外键)的又一变体:
**这次漂移的不是字段值或匹配逻辑, 而是"数据集合的边界"本身**——边界不一致时,
门控声称的"全库已校验"是假命题。

## 解决方案

`kb.entry.iter_entry_paths(repo_root)` 成为条目发现的**唯一事实源**(布局契约:
条目只住 `kb/<type>/...`, 点目录是外仓不进父仓视野), lint/index/gate(查重+`_find`)/
query(待复核+待上提) 六个读源全部改接; 回归测试直接断言"各读源可见集合必须相等"
(结构性防漂移, 而非各处贴注释约定)。

关键配套: 统一后散文件从"进检索免检"翻转为"谁都不看见"——**静默失踪比免检更糟**,
所以 lint 新增 `stray_entry_paths` 检查, kb 根直下带 id 的 .md 显式报错点名
("请移入条目目录"), 两端都堵。

## 验证

探针修复前 `index 收录=[b002, b001, g001] / lint 对坏文件报错数=0`; 修复后
`index 仅收 g001 / loose.md 被 lint 点名`, `.mounted` 外仓维持"不进父仓视野"设计内
语义。回归 test_lint.py +2(散文件点名+排除 / 四读源集合一致性), pytest **306 全绿**;
真实仓(当前恰无散文件)`index --check` 两处无漂移、lint 两处通过。

## 适用边界与反例

适用于任何"质量门控(校验/lint/CI 检查)与消费链(索引/检索/构建)各自枚举数据集合"
的系统: 代码 lint 的 glob 与打包工具的 glob、测试发现规则与 CI 触发规则、schema
校验遍历与迁移工具遍历。**判据: 门控说'全库通过'时, '全库'与消费方加载的集合是否
同一函数算出来的**。若两处枚举由不同人不同期写就, 默认当作已经漂移, 先做集合差分。

反例: 有意为之的宽窄不同(如构建时排除 test 数据)是合理需求, 但必须在代码里显式
声明差异来源(如 `paths = iter_all() - EXCLUDED`), 让差异可审——本缺陷的坏在"无人
声称差异存在过"。

## 新发现(第二十七轮走查 §45): 漂移的不只是"集合的枚举", 还有"比对的参数"

同族第三个变体, 这次漂移发生在**门控重算时传入的参数**上: `kb doctor` 的 index
fresh 检查用 `check_indexes(kb_base, repo_name=业务仓根名)` 重算期望内容与
index.jsonl 现值比对, 而生产方 `kb index` CLI 的默认口径是 **kb 载体目录名小写**。
业务仓标准结构 `myproject/docs/kb/` 下两口径恒不等("myproject" ≠ "docs")——
**doctor 对刚 `kb index` 过的仓恒报 stale**, 且按 WARN 建议的命令(`kb index --repo
docs`, 载体名口径)重建后仍然 stale: 修复动作本身永远消不掉误报, 自检把"照做就能
绿"的承诺变成了死循环。

隐蔽性来源与集合变体同构: **主仓自测恰好载体目录=仓根(kb 在仓根, 两个名字算出来
一样)**——dev 环境永远绿, 只有业务仓(docs/kb 结构)接入才发作。第一触点面(doctor)
误报比漏报更伤: 新人接入第一天就收到"照建议做完还是红"的信号, 对整个工具链的
信任直接崩塌。

判据补强: 前文判据说"两边集合必须同一函数算出来", 本变体推广为——**"比对"操作的
两侧, 连比对所用的参数(名字/口径/基准)都必须同源**。`check_indexes(A, name=X)`
与 `build_indexes(A, name=Y)` 只要 X/Y 来自不同表达式就是缺陷, 哪怕 X==Y 碰巧成立。
修法即把 doctor 的取名表达式改成与 CLI 默认口径一致(载体目录名), 并在注释里点名
"必须与 kb index CLI 默认口径一致"锚住。

## 新发现(第四十五轮走查 §63): 失踪点名判据"只认可解析 id"——坏得越彻底越隐身

§42 配套的反失踪检查 `stray_entry_paths` 本身的判据又漏了一种失踪: 判据是
"kb 根散文件且 **可解析出 front-matter id**"。于是 front-matter YAML 语法坏的
散文件(未闭合流/tab 缩进)完全静默——它同时滑了**位置**与**语法**, 是作者"显然
想写条目"的两证齐全样本, 却比只滑位置的失踪得更彻底: 不进 index(布局契约排除,
符合设计), 也不被 stray 点名(解析不出 id), 还不触发 lint 的语法错误消息(那条
只覆盖 iter_entry_paths 内的条目)。探针实测: 完好散文件被点名, 语法坏散文件
零输出, 无 front-matter 的纯笔记同样零输出(设计内)。

一般化判据: **"点名条件建立在可解析性上"的失踪/异常检测, 对'坏得最彻底'的
样本天然失明**——越该报警的样本越解析不出报警所需的字段, 形成"完好者被点名、
残骸者隐身"的倒挂。修法是把判据从"解析成功且带 id"放宽为"带 id **或** 解析
失败"(parse 层已把 YAML 语法坏降级为 `yaml_error` 携带原文, 判据直接复用),
lint 消息按实际分叉措辞("带 id 但不符合…" / "front-matter 语法坏但不符合…"),
无 front-matter 的纯笔记(fm={} 且 yaml_error=None)不受误伤。

这与 §53"修复让问题隐身须显式点名"是同一元规则的两次应用: 归一化/降级让消费链
存活的同时, 也让病因从常规校验通道隐身——**每加一层降级, 就要为降级样本单独
建一条点名通道**。
