# 条目解析器不容错致单坏文件全库命令崩溃或静默隐身

## 背景 / 现象

知识库条目是**人手编辑**的 markdown+front-matter, 解析器 `parse_entry` 却按可信输入
对待。第十三轮走查实测两类爆炸半径:
1. **一个 YAML 语法坏的条目**(缩进/tab 手滑): `kb lint`/`kb index`/`kb stat` 全部
   Traceback 崩溃; `kb search` 退化成**静默空库**(exit 0 返回 `[]`)——用户搜不到东西
   却被告知"库里没有", 病因藏在别处;
2. **一个带 UTF-8 BOM 的条目**(Windows 记事本/PowerShell `Set-Content` 存盘自带):
   不崩、不报错、不进索引——条目**静默隐身**, `kb index` 显示 wrote 成功, search 永远
   查不到它。

## 根因

同一函数的两个不容错点(`entry.parse_entry`):
1. `yaml.safe_load` 抛 `YAMLError` 无捕获, 沿 23 处消费方(lint/index/gate/query/
   search-evaluate...)裸穿; search 的"空库"假象是 index.jsonl 被坏文件挡住无法重建
   的下游结果——**崩溃点与症状点分离**, 排查极易跑错方向。
2. `read_text(encoding="utf-8")` 遇 BOM 留下 `\ufeff`, front-matter 正则 `^---` 不匹配
   → 按"无 front-matter"降级 → `index` 对无 id 条目**静默跳过**(设计本意是容忍草稿,
   这里却吞了编码问题)。BOM 是 Windows 生态第一隐雷: 同一份文件 Linux/macOS 无恙,
   用 Windows 编辑器保存一次即坏。

## 解决方案

- `read_text(encoding="utf-8-sig")`: 有 BOM 剥掉, 无 BOM 行为不变(一行修隐身);
- `YAMLError` 捕获降级 `fm={}` + `yaml_error` 记入 Entry: 消费方全部存活, 坏文件
  走"缺必填"路径可定位;
- lint 对 `yaml_error` **跳过 schema 校验**并直接报
  `文件名: front-matter YAML 语法错误: <原文>`——若只靠 schema 报"缺必填", 用户会去
  补字段而修错方向(报错要指向真病因, 不是第一层症状)。

## 验证

- 探针(正常条目+坏 YAML 条目, 5 个 CLI 子命令): 修复前 lint/index/stat=CRASH、
  search=静默空库、show=not found(殃及无辜); 修复后全部正常, lint exit 1 且首条错误
  即"front-matter YAML 语法错误"(带文件名与 YAML 消息);
- BOM 端到端: 带 BOM 文件 index→search 全链路命中(修复前 index.jsonl 无此条、
  search 空); 回归 `test_bom_tolerated`/`test_broken_yaml_degrades_not_crashes`,
  pytest 288 全绿。

## 适用边界与反例

适用于一切"解析人手工编辑文件"的系统(配置、front-matter、清单)。判据: 解析器必须
把**单个文件的坏**限制在**该文件的影响**内——批量消费入口(遍历目录)处逐条容错并
上报"哪个文件坏+坏在哪", 而不是让异常穿透整条命令。尤其警惕"崩溃点与症状点分离"
(坏文件挡住索引重建→检索说没有): 症状层修复(加告警)前先看根因层(解析器)能否降级。
反例: 机器生成且被上游校验保证的文件流可在解析器保持严格(fail-fast 暴露上游 bug);
区分标准是"坏文件是否可由作者当场修复"——人手编辑的必须可定位, 不可静默。
