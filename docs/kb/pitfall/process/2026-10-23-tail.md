# tail 读模式复制粘贴: 修一处只给一处站岗, 第二份拷贝潜伏十六轮

## 背景 / 现象

同一"tail 增量读 JSONL"模式在仓内有两份拷贝: `serve.py` 的 TraceWatcher(面板
SSE 推流)与 `spider_live.py` 的 run 循环(蜘蛛直播桥)。第十二轮走查在 serve 侧
实锤并修复了"半行被吞 → 行补全后事件永久漏推"(§30, tail 语义 + 二进制偏移),
但 spider_live 里的同款循环原封未动。第二十八轮探针实测同一脚本喂半行:
`offsets[f] = fh.tell()`(文本模式)推进越过未写完字节, 行补全后该事件在直播流
**永久漏播**——同一缺陷潜伏了十六轮。顺带挖出拷贝特有的两个兄弟缺陷:
首见文件 birth 判定 `st_ctime >= time.monotonic()`(epoch 秒与 monotonic 秒
不同钟系, 恒 False → 每次启动把全部历史 trace 从头回放, 会话洪泛);
脏事件(`returned:null`/`ext:null`)未经 `_coerce` 归一直接进 `_dispatch`
抛 TypeError, 且循环无逐事件防护 → **一条脏行让整个直播进程崩退**
(serve 侧同类风险早在 §26 就修了, 又是只修了一处)。

## 根因

复制粘贴的模式不会随原件一起进化。修 serve 时缺陷清单只作用于"触发现场",
没有任何机制(共享函数/共同测试)把 spider_live 的拷贝拉进修复半径。这正是
第二十六轮沉淀的 D-28 判据("改变同一事实的写路径必须全仓普查")的反向情形:
**判据不只适用于写路径挂账, 也适用于"修过的模式"——修一处时应当即 grep 该
模式的指纹(如 `fh.tell()`、`seek(pos)` + `splitlines`)找齐所有拷贝**。钟系
缺陷则暴露拷贝时的"顺手改造": serve 用 `time.time()` 是对的, 抄到 spider_live
时因 run 循环已有 `t0 = time.monotonic()`(用于 max_sec 超时, 用途正确),
开发者顺手复用 t0 做 birth 判定——两个钟系各有用途, 混用即错, 且单调钟差值
在测试里(启动即时写入)恰好也能"看似合理"地通过肉眼看代码。

## 解决方案

- run 循环对齐 serve 的 tail 语义: 二进制读、`rfind(b"\n")` 截到行边界、
  偏移只推进到 `pos + cut + 1`, 无完整行偏移原地不动; 补截断检测(`size < pos`
  重置)。
- 新增 `birth = time.time()` 与 `t0`(monotonic)分离, birth 判定只与 wall-clock
  比; 注释点名"必须与 st_ctime 同钟系"。
- 分发前过 `kbtrace._coerce(ev, [], f.name)` 与 serve watcher 同口径归一,
  `_dispatch` 外加逐事件 try/except——单条坏事件跳过, 直播循环续跑。
- `event_to_updates` 的 `returned`/`layers`/`ext` 改 `or []`(`.get` 默认值对
  "键存在但为 null"不生效)。
- 回归 4 个: 半行补全后必须补播 / 历史文件不回灌 / 毒事件后续播 /
  null 字段不抛(test_spider_live.py +4)。

## 验证

探针修复前: 半行补全后 `create_session` 数=0(永久漏播), `ext=None` 与
`returned=None` 均抛 TypeError; 修复后补播=1、两脏事件均不炸、毒事件后
"好"事件仍开播。pytest **317 全绿**(313+4), ruff `--select F,E9` 通过。

## 适用边界与反例

适用于任何"同一逻辑模式在仓内 ≥2 处拷贝"的场景, 尤其是 tail 文件、增量游标、
重试包装这类"看起来人畜无害的十行循环"。**判据: 修一处模式缺陷时, 先按代码
指纹(grep 关键调用组合)枚举全部拷贝, 再决定修复半径**; 更根本的解法是抽公共
函数(本例两处暂未合并——serve 与 spider_live 的消费动作不同, 抽读取器收益
有限, 已用注释互指锚定 §30/§46)。反例: 一次性脚本的拷贝不必回改, 但前提是
能明确论证它不在"同一事实源的第二消费方"位置上。

## 新发现(第三十二轮 §50: 同一判据的"字段维度"形态——净化只做一个字段)

同一缺陷家族的第三种拷贝形态: 第十二轮 §26 在 trace 解析期做脏输入归一
(`_coerce`)时, 只处理了 `returned=null`, 其余列表字段(`layers/ext/suggest/read`)
原样入缓存——第三十二轮逐屏走查用一份 `layers: null` 的脏事件把 `/api/stats`
打成 500(`stats.top_consumed` 的 `s.get("layers", [])` 炸 TypeError)。

两层判据各命中一半:
- **字段维度普查**: 当年修 `returned` 时, 应把事件 schema 里**所有列表字段**
  一起归一, 而不是只修触发处——"拷贝"不一定是整段代码, 也可以是"同一净化
  名单只列了一个字段"。判据仍是同一句话: 修一处模式缺陷前, 先按缺陷指纹
  (此处=可空列表字段)枚举全部暴露面。
- **`.get(k, 默认值)` 对"键存在但为 null"不生效**: JSON 客户端把空值序列化成
  `null` 而非省略键时, `get(k, [])` 返回 `None`, 默认值形同虚设。消费方一半
  写 `.get(k, [])` 一半写 `get(k) or []`——与其逐点补防, 不如在**不可信输入
  进缓存/入库前**把口径统一归零(一次净化, 全体消费方终身受益; 新增消费方
  不再踩)。

教训固化成一句话: **净化器的名单要对着 schema 全量列, 不能对着事故增量列**
——事故驱动的白名单永远慢一步。

## 新发现(第三十四轮 §52: 净化思想推进到写面——"入缓存前"升级为"入账本前")

§50 判据的又一次兑现, 这次轮到 **ingest 写面**(/api/ingest, 团队态上报口):
身份字段不做类型契约——`trace_id=list` 在幂等 key 元组构造处 TypeError
(handler 线程崩 → 连接重置, §26 家族首次出现在**写侧**); `caller_repo=dict`
更阴险: 写侧 200 照收、落盘入账本, 读侧 `by_caller.setdefault(dict)` 再把
每个读端点打崩 500。"写侧宽容、读侧崩"是账本类系统最坏的失败组合——污染
是持久的, 崩溃是复利的。

本轮执行 §50 判据比上次完整: (a) 写面 fail-loud 拒收(六个身份字段
`trace_id/id/caller_repo/layer/source/ts` 非 str 即 400, 对着 schema 全量列
而非只列触发的 trace_id); (b) 读面 `_coerce` 同批净化存量脏文件(修复前已
入账本/手工写入的 dict 键降级为"项目未知"+warn)——**写面拒收只管未来,
账本里已有的脏数据必须读面兜底**, 两条腿缺一条都会残留 500。

判据再补一句: **账本型系统(事件日志/消息队列/CDC)的类型校验必须写在入口,
且入口拒收与存量净化成对出现**; 只有前者=旧账继续崩, 只有后者=新账继续进。

## 新发现(第三十五轮 §53: 净化家族第四形态——front-matter 列表字段退化, 故障是"假通过"而非崩溃)

同一判据落到**知识库自身的输入面**(front-matter YAML), 但故障形态升级: 不再
崩溃, 而是**静默给出错误答案**。手改 YAML 把列表写成标量(`domain: frontend`)
或留空(`tags:` → null)时:

- `"front" in "frontend"` 子串真 → `search(domain="front")` **假通过**;
  `related: kb-…-aaaa`(标量)让 `"kb-…-aaa" in "kb-…-aaaa"` 截断 id 假命中——
  `in` 运算符对 str 是子串、对 list 是成员, 退化无感切换语义(§51 的开关子串
  洞在数据面的重现);
- `Counter(d for r in recs for d in r["domain"])` 把字符串拆成**字母计数**
  (`{'f':1,'r':1,'o':1,...}`), stat 报表安静地错;
- lint 的 schema 校验能报(not of type array), 但消费链在报错的同时照常失真
  ——**门控报了 ≠ 消费链安全**, 读路径不能假设 lint 跑过且全绿(存量文件/
  绕过 lint 的写入)。

修复 = §52 判据第三次完整执行: `parse_entry` 单一入口对 schema 全量列表字段
(`domain/tags/related`)归一(标量→单元素列表、null→删键、脏元素剔除), 退化
描述记入 `Entry.list_degraded` **由 lint 显式点名**——关键设计: 归一让 schema
校验看不到病因, 若不一并报出, "修复让问题隐身"比不修更糟; 净化器必须与
点名器成对。

判据补第四句: **列表字段与 `in` 运算符共生的系统, 解析入口就要把"可能是
标量"的输入归一成列表**——成员判断的正确性不能依赖数据作者的 YAML 素养。

## 新发现(第三十七轮 §55: 净化器与消费方的暗雷——"删键"策略让硬索引消费方成雷区)

§52/§53 的净化器用"**删键**"处理坏值(让下游 `.get(k, 默认)` 生效), 这个决策
本身埋了新雷: **任何 `ev["key"]` 硬索引消费方从此都可能 KeyError**。第三十七
轮探针实测 spider 回放链两处炸: get 被删 `id` 键 → `g["id"]` KeyError;
search 被删 `trace_id` 键 → `search_ev["trace_id"]` KeyError——回放屏整个掐
断。同轮另一族: `_coerce` 名单没覆盖 `query` 非字符串(list 做 Counter 键
TypeError、`.strip()` AttributeError), `stats.top_queries/zero_hit_board`
崩——正是 §50"名单对着 schema 全量列"欠下的最后一块。

判据补第五句: **净化器选择"删键"策略时, 必须普查全体消费方的硬索引访问
(`ev["k"]`)并降为 `.get`**; 净化(改数据形状)与消费(读数据形状)是一体两面,
改形状的那一刀必须同时清点所有读这把形状的手。更省心的替代: 净化时**保留键
写空串**(删键→置默认), 硬索引读到的就是合法空值——代价是消费方无法区分
"缺失"与"坏值", 对"尽力呈现"型消费方(回放/直播)置默认更稳, 对需要区分语义
的消费方才用删键。本轮两处消费方(spider_export/spider_live)按前案统一降
`.get`+类型守卫, 未动净化器形状(删键语义已被 §52 回归锁定)。

## 新发现(第三十八轮 §56: 净化家族第六形态——校验只装在一个入口上, 另一个入口裸奔)

同一字段在不同**写入口**上的防线不等厚: `severity` 在 CLI 面由 argparse
`choices` 把守, MCP 面(kb_create/kb_update)与 gate 函数本身**零校验**——
探针喂 `severity='blocker'`/`'紧急'` 一路落盘并写进 draft 索引, lint 事后才
报 schema 违规, 而索引污染已经发生。这不是"忘了加校验", 而是**校验被放错
层**: argparse 是 CLI 的入口守卫, 不是数据面的; 数据面有多个入口(CLI/MCP/
未来的 HTTP 写面)时, 每个入口都得有, 或者下沉到唯一写函数。

同族先例即 §52(ingest 写面身份字段): 那次是"读面净化了写面没拒", 这次是
"CLI 面拦了 MCP 面没拦"——**同一份数据契约的守门强度必须按"最弱的合法入口"
对齐**, 因为攻击者/事故永远从最弱入口进来。

判据补第六句: **对受枚举/类型契约约束的字段, 校验要放在所有入口共用的最后
一跳(写函数入口), 而不是各自入口各写一份**; 暂时做不到(如 argparse 的
choices 顺带提供 --help 提示)就两处都要, 并让程序化校验以唯一事实源
(taxonomy.yaml)为准, 不许在第二处抄一份枚举值字面量。本轮 `_check_severity`
落在 `create_draft`/`update_draft` 头部, 枚举读 taxonomy, CLI 的 choices 保留
(它同时服务人类提示), 两处语义同源。

## 新发现(第三十九轮 §57: 净化家族第七形态——数据隐藏承诺只装了一条发现通道)

红线1 说"status: draft 的条目不进检索索引", 于是 `kb_search` 只读
index.jsonl(live 池), draft 从检索隐身——**但索引行的输出通道不止 search 一
条**: `query.related` 读 `_records` = live+draft 双池(反向环需要 draft 行才
能引用), 于是 draft 条目经 related 字段**双向**泄漏——accepted 正向引用草稿、
或草稿反向引用 accepted(环把草稿行带出), kb_related/kb related 都把未发布
草稿的标题+摘要端给 agent。探针实测两条泄漏路径全中, 检索面却干净: 同一个
"草稿不出土"承诺, 一面守一面漏。

这是 §56"守门强度按最弱合法入口对齐"的**镜像形态**: §56 讲写面多入口的校验
不等厚, 本例讲**读面多出口的过滤不等厚**——而且读面更隐蔽, 因为"隐藏"类
承诺的验证习惯是"在承诺声明的那一面测"(search 搜不到 = 以为安全), 很少有人
把同一份索引行的每条输出路径(kb_related / 面板 / 导出)都拿同一个 draft 样本
过一遍。

判据补第七句: **每加一条"从不可信池读全量再输出"的通道, 都要回头对照既有
的隐藏承诺逐条补过滤**; 更可靠的做法是把"哪些行可见"下沉成共享谓词
(如 `visible(r)`), 让所有出口调同一个函数, 承诺只写一次。本轮在 related
出口按 `status != draft` 剔邻接行(self 可为 draft: 人工问自己的草稿, 邻人
照报), get 面不动(已知 id 的读取面, 非发现面)。

## 新发现(第四十轮 §58: 净化家族第八形态——参数值域不设防的两种静默故障)

§56 判据("数值参数的值域契约只能由被调方自己守")在 CLI/serve 参数面挖出
两个实锤, 故障形态都**不是崩溃而是静默出错**:

1. **Python 负数切片翻转语义**: `read_traces(limit=-2)` 落到 `searches[:-2]`
   ——"去掉尾部两个"而非"取前 -2 个", `kb trace list --limit -2` 返回**全量
   减 2 条**: 调用方要"最少"得到"最多", 方向完全翻转。argparse `type=int`
   只保证是整数, 负号照过。同族第三处(§51 sources、§56 layers 之后)。
2. **非法过滤值静默滤空=与真空不可区分**: `--since 2026-13-99` 参与
   `ts[:10] >= since` 字符串比较, 全部事件被滤光、exit 0——"暂无 trace 记录"
   冒充"该窗口没数据"; `kb trace report --since 垃圾` 更糟, 零命中榜空 →
   输出"本窗口零命中已全部消化 ✅"**假绿**。字符串比较式过滤对格式错误
   天然宽容(任何串都能比), 坏参数与空结果在输出面上同形。

判据补第八句: **参与比较/切片运算的参数, 值域校验必须做在入口且 fail-loud**
(argparse `type=` 函数 / HTTP 400), 因为这两种运算对"错值"都不抛异常: 切片
把负数解释成反向语义, 字符串比较把错日期解释成"全都过滤掉"。**尤其警惕
"坏参数 → 空结果"路径——空结果在展示层就是合法空态, 假绿比报错危险**;
宁可 exit 2 让用户改命令, 不可 exit 0 让用户信一个编出来的"没有/已消化"。

## 新发现(第四十二轮 §60: limit 家族第四处 + 客户端错误伪装 500)

limit 契约同族 hunt(§51 sources → §56 layers → §58 trace → 本轮 feed)再中
一处, 且暴露该族的**第三种故障形态**:

1. **负数切片翻转再现**: `stats.feed_events(limit=-2)` 的 `[:limit]` 与 §58
   同款(第四处)。同一表达式在四个模块独立出现, 每处都要靠被调方自己守——
   再次佐证"契约只能由被调方守"且**新入口会不断重新引入**。
2. **客户端错误伪装成服务器故障(新形态)**: `/api/feed?limit=abc` 被
   `int(q.get("limit", 50))` 炸成 500 `internal: ValueError`。区别于前两种
   静默形态: 这次**有报错但状态码撒谎**——4xx 的输入问题穿 5xx 的衣, 面板
   显示"internal:"让用户以为服务端坏了。判据补: **入口做类型/值域校验不仅
   为了 fail-loud, 更为了让错误归位**——"坏输入 → 意外异常 → 兜底 except
   回 500"路径里, 兜底处理器无法区分"数据坏了(500)"与"参数错了(400)"。
   显式入口校验把这条模糊路径在源头截断。

判据(第八句的推论): 值域校验宜"入口拒收(400/exit 2) + 被调方归一(≤0 零
名额)"成对出现——前者管错误归位, 后者管直调面(不经 HTTP 的 import 调用)
兜底。

## 新发现(第四十三轮 §61: limit 家族收口——第五处与"逐处 hunt 会漏")

第四十二轮说"四模块独立出现"后, 按 `[:limit]` 表达式全仓穷尽再 hunt, 又中
第五处: `search.search()`(公共库 API)的 `rows[:limit]`——**恰好是全族唯一
没有任何调用方面试的裸入口**(sources/layers/trace/feed 都至少有一个工具面
间接触发过测试, 而 search() 的 limit 只被正数测过)。同族 hunt 的教训升级:
**"修了 N 处同族"本身就是漏第 N+1 处的认知陷阱**——每轮修复后应以"表达式
文本"(`[:limit]`/`.find(` 等)而非"记忆中的模块清单"做全仓穷尽, 表达式是
有限集, 记忆不是。修复后全族五处(sources/layers/trace/feed/search)统一
"≤0 零名额"契约并有测试锚点。

## 新发现(第四十四轮 §62: §56 判据第二次命中——confidence 枚举静默忽略)

severity 守门(§56)落地后按同判据 hunt 其余枚举入参, confidence 中招且形态
更阴: review() 的 `if to == "accepted" and confidence in ("verified",
"probable")` 对非法值**静默跳过提升**——`confidence='verifed'`(拼错)时条目
照常 accepted、verification 留痕照常写, 唯独调用方最关心的字段提升没发生。
severity 至少是"垃圾值落盘可被 lint 事后点名", confidence 是"合法值保持
原样+动作成功回执", **连事后可发现性都没有**——探针证实 accepted 后索引里
仍是 probable。

判据升级: 同一"入口防线不等厚"模式在第二个参数、第二个函数重现, 说明逐
参数修补追不上新增速度——应固化为**清单式普查**: 公开写函数的每个枚举入参
(create_draft/update_draft/review/…)统一过 taxonomy 校验, 新增参数时清单
即检查单。

## 新发现(第四十六轮 §64: "全族收口"宣言自己成了陷阱——同文件三榜单漏网)

§61 写下"全族五处收口"后, 第四十六轮再按 `[:limit]` 表达式对账, **同一文件
stats.py 里还有三处裸 `[:limit]`**: top_queries / top_consumed / zero_hit_board
(feed_events 在 §60 修过, 同文件其余三个榜单没人看)。探针实锤 `limit=-2` 让
三榜单返回"全量减 2"。这次连"记忆中的模块清单"都不是失因——§60 修 feed_events
时整个 stats.py 都在屏幕上, 视线只落在了被报障的那个函数上。

判据再收紧一档: **"修完并宣布收口"这个动作会提前关闭你的搜索**——收口宣言
写下的瞬间, 该表达式家族在你心里已经"处理完了", 而表达式实例数不因宣言减少。
正确姿势是把"穷尽"变成每轮的机械动作而不是"收口时的一次性动作": 每轮修复后
对整个 `src/` 重跑一次表达式 grep, 把命中逐条对照守门代码, 对不上就立靶——
本轮三处正是这样撞出来的。修复后全族 `[:limit]` 表达式共八处受契约锚定
(sources/layers/trace/feed/search/top_queries/top_consumed/zero_hit_board),
测试锚点逐函数覆盖。

## 新发现(第四十七轮 §65: 净化家族的"灯下黑"——净化了数据行, 漏了文件头的元数据行)

§26 给 trace 事件行建了完整的 `_coerce` 净化(null/非列表/非数值/容器 query
全兜住), 但**同一文件的 meta 首行**走的是另一条更原始的代码路径: `meta.get(...)`
对 JSON 数组首行直接 AttributeError、`int(meta.get("schema"))` 对 `schema:"v2"`
直接 ValueError——`_parse_file` 爆炸沿 `read_traces` 上炸, stats/feed/callers
三端点全挂, **爆炸半径与被净化保护的事件行崩掉完全相同**。探针两种脏 meta 均
实锤整库读崩。

形态命名: **"净化器只覆盖它被编写时盯着的那部分输入"**——"文件是不可信输入"
这个正确认知落地时, 作者的视野停在"事件行"(量大、字段多、刚被报障), 文件头的
元数据行被潜意识归为"我们自己的写侧产的, 可信"。而现实是 meta 行与其他行同经
手工编辑/异构客户端/半文件复制, 可信度完全相同。判据: **净化以"输入边界"为范
围单位, 不以"字段多少"为单位**——审一遍净化器时问"这个边界内还有哪些解析路径
没经过它"(本例: 同一个 open+splitlines 喂出的两条解析分支, 一条有防一条裸奔),
而不是"这个函数里的字段都防全了没有"。修复保持既有容错哲学: 非数值 schema 按
本地版本兼容读取+warn(读不懂版本标记不等于数据坏), 非对象 meta 行按缺 meta 跳过。

## 新发现(第四十八轮 §66: 同一函数相邻两行, 对同一数据建了两种厚度的防线)

`spider_export.to_record` 里紧邻的两句: 上句 read_ids 对 `g.get("id")` 做了
`isinstance(..., str)` 守卫, 下句 consumed 集合推导却裸取 `g["id"]`——§52 净化
删掉 id 键的 get 事件(JSON 合法路径), 只要 returned 里混进一个 null 元素
(`_coerce` 不清理列表元素), `None in returned` 判真, `g["id"]` 直接 KeyError
掐断整条回放(/api/replay、/api/spider 500)。探针实锤后补守卫, 复验存活。

形态命名: **"同函数第二行"**——§62 判据全仓普查"清单式而非逐参数", §64 判据
"修完一处视线即离开", 本例是其微观终态: 视线单元可以缩到**一个函数内的相邻
两行**。作者写守卫时心智模型是"这个表达式防过了", 而防线是**表达式级**的,
不是"数据级"的——同一份 `get_evs` 在本函数内被消费两次, 第一次穿了防弹衣,
第二次裸奔。判据: 修完某行对变量 X 的守卫后, 立即在本文件 grep X 的**全部**
其他消费点, 逐点确认防线等厚; 代码评审时凡是"上一行 `.get(k)` 下一行
 `[k]`"的相邻对, 直接按缺陷读。

## 新发现(第四十九轮 §67: "同函数第二行"的跨模块形态——净化器的删键契约没有下游消费清单)

§66 判据在下一轮就独立重现, 且换了尺度: `trace._coerce` §52 明文规定
trace_id 非字符串**删键**, 而 `cli.py` 的 `trace export --latest` 拿
`read_traces` 结果后裸写 `newest[0]["trace_id"]`——最新事件恰是坏 trace_id 时
(越坏的样本越会被 `_newest_first` 排到最前), KeyError 未捕获直接 traceback。
探针实锤: 同一数据 `trace list` 正常输出(trace 面全用 `.get`), `export
--latest` 崩。修复: 取键后校验非字符串即如实报错退 1, 引导显式 `<id>`。

判据升级: **净化器的"删键"是对全仓下游的契约变更**——它在源头把"键可能缺失"
变成不变量, 而消费点散布在其他模块, 写净化器的人不会想到 CLI 层三文件外的一
行。机械化做法: 净化器每新增一个删键分支, 对该键名做全仓 `["<键>"]` 裸索引
grep(本轮 `["trace_id"]` 全仓恰好只有这一处命中, 一击即中); 评审时反过来, 看
到 `ev["k"]` 先问"k 是不是净化可删键"。与 §66 合并为一条完整规则: **防线审计
的视线单元从"相邻两行"扩到"生产者-消费者全链"——源头声明可缺的键, 所有裸索
 引点都是债**。

## 新发现(第五十轮 §68: 全链普查的第二猎物在生产者侧——聚合函数自己往集合里塞 None)

按 §67 的机械动作(净化可删键逐个全仓普查消费点)扫 `["id"]` 时, 顺路审到消费
集合的**生产者** `_gets_by_trace`: 它 `add(g.get("id"))` 不看类型, 把净化删键的
None 塞进"已消费 id 集合"。三个下游三种死法——top_consumed 判 `g["id"] in
consumed` 时 None 命中真分支再裸取 KeyError; feed_events 的 `read` 列表遇
None+str 混合 `sorted()` TypeError(单 None 时还悄悄输出 `[null]` 污染 API);
aggregate 的 consumed_total 把 None 记成一次真实消费(**KPI 虚高, 不崩但说谎**,
比崩更隐蔽)。探针三场景实锤, 生产者侧一行 `isinstance(gid, str)` 全收口,
复验干净。

判据补全 §67 的另一半: 净化删键的下游债不只有"裸索引消费点", 还有**"把可缺
值装进有类型语义容器"的生产者**——集合/字典键/排序数组一旦混入 None, 伤害沿
容器传播到所有读取方, 且症状分裂(KeyError/TypeError/静默脏数据三种)。审一个
删键分支时要问两句: "谁裸索引这个键"(§67)与"谁把这个键装进容器再分发"(§68)。
装容器处就是该键的类型收敛点, 在这里守一次, 胜过消费方逐点补防。
