# 红线校验对整坨JSON扫子串误杀同名单值叠加尽力中继静默吞成无声丢数据

## 背景 / 现象

观测面板 ingest 上报口(`/api/ingest`)有一条红线: 拒收含正文的 trace(PRD 原话"正文**键名**
拒收")。早期实现把整个事件 `json.dumps(...).lower()` 后用
`any(f'"{k}"' in flat for k in ("body","content","text"))` 判断。第十轮走查实测:
`query="content"`(合法检索词, 团队态下用户真会搜这个词)被 400 拒, 而这条 trace 在团队账本里
**彻底消失且无任何告警**——本地账本有, 团队账本永久缺这一条。

## 根因

两层缺陷叠加成"无声丢数据", 单独任一层都不致命:

1. **误杀**: 红线本意只查 dict **键名**, 实现却对序列化后的整坨字符串扫子串 → 值也扫。
   `query="content"` 序列化成 `"query": "content"`, 内含子串 `"content"` → 误命中红线。
   合法检索词恰等于 body/content/text 时必被拒(实测 Q0/Q1/Q2 三个单词全 400,
   而 `query="正文 content 规范"` 因 `"content"` 不成对引号包裹反而放行, 说明命中纯看
   引号相邻, 与语义无关)。
2. **静默**: 客户端 `_post_ingest` 对上报失败 `except Exception: return` 静默吞
   ("绝不反向影响检索"的设计), 400 也吞。误杀 + 静默 = 数据永久丢失但两端都不报错。

## 解决方案

递归只查 dict 键名, 不碰值:

```python
def _has_body_key(o) -> bool:
    if isinstance(o, dict):
        return any((isinstance(k, str) and k.lower() in ("body","content","text"))
                   or _has_body_key(v) for k, v in o.items())
    if isinstance(o, list):
        return any(_has_body_key(x) for x in o)
    return False
```

实测值放行(`query="content"` 等全 200)、任意深度嵌套键名仍拒(`layers[].matched[].content`
→ 400)、大小写变体键名(`Text`)也拒。回归 `test_ingest_body_key_redline_checks_keys_not_values`。

## 验证

- 修复前(实测): `query="content"/"text"/"body"` 三个合法检索全被 400(探针逐条打),
  而 `query="正文 content 规范"` 放行——命中纯看引号相邻, 与语义无关;
- 丢失链路(代码阅读): `_post_ingest` `except Exception: return` 吞掉 400 → 团队账本缺失
  无告警为必然结果;
- 修复后(E2E 实测, 走客户端真实路径 `append_event`, query="content"): 团队账本收到
  1 行, 重发幂等仍 1 行, 本地落盘不受影响。
pytest 283 全绿(+1 回归)。

## 适用边界与反例

适用于一切"红线/白名单校验"。判据: **校验作用域必须与意图一致**——"禁正文键名"就只遍历
dict 的 keys, 绝不能 `dumps` 后扫子串(值、转义、嵌套结构全成误判源)。更危险的组合是
"服务端误拒 + 客户端静默吞": 任何尽力而为的旁路上报, 配一个会误杀的校验, 等于开了个无声
数据黑洞。反例: 若确实要禁正文**内容**(而非键名), 则应显式定义正文在哪几个字段并只查那些
字段值, 仍不能全局扫子串。
