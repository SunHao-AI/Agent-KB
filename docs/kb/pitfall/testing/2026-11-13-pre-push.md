# 测试未清开发机环境变量, 读到真实凭据致 pre-push 门禁卡死

## 背景 / 现象

Agent-KB 仓 pre-push 门禁跑全量 pytest(无豁免)。本机 shell 设过真实 `KB_SERVE_TOKEN`
(观测面板令牌)后, `tests/test_stats_serve.py` 中 3 个 `test_userconf_*` 用例必挂:
断言 `serve_target()` 返回值等于写入 tmp_path 配置文件的值, 实际返回的却是**真实
token**——失败输出直接暴露真实凭据。用例在 CI/他人机器全绿, 只在这台开发机挂,
容易被误判为"环境问题"而想走 `PREPUSH_SKIP` 逃生口。

## 根因

被测函数 `src/kb/userconf.py` 的 `serve_target()` 读取优先级是
**环境变量 > 配置文件**(便于临时覆盖): 先 `os.environ.get("KB_SERVE_URL"/"KB_SERVE_TOKEN"...)`,
环境变量非 None 时直接生效, 配置文件值被顶掉。用例只隔离了配置文件路径(monkeypatch
到 tmp_path), **没有清进程环境变量**——凡开发机 shell 恰好设过这些变量, 断言"读到
tmp_path 写入值"就必挂。本质是测试对被测代码的"环境优先级"维度无隔离, 测试结果
依赖开发机隐式状态, 不可移植。

## 解决方案

按同文件既有 roundtrip 用例先例, 给 3 个用例补 `monkeypatch.delenv`:

```python
def test_userconf_hash_in_values_survives_roundtrip(tmp_path, monkeypatch):
    monkeypatch.delenv("KB_SERVE_URL", raising=False)
    monkeypatch.delenv("KB_SERVE_TOKEN", raising=False)
    monkeypatch.delenv("KB_INGEST_URL", raising=False)
    monkeypatch.delenv("KB_INGEST_TOKEN", raising=False)
```

另两个用例按其断言涉及的变量同样补 `KB_SERVE_URL`/`KB_SERVE_TOKEN`。
通则: **被测逻辑读环境变量时, 用例必须显式声明对哪些变量做 delenv(或 setenv)
隔离**, 不能假设"测试机不会设这个变量"。

## 验证

- 修复前: 本机 `python -m pytest tests/test_stats_serve.py -k userconf` 3 failed,
  失败值 == 真实 token(即泄漏证据)。
- 修复后: 全量 `python -m pytest -q` 492 passed 无豁免; pre-push 门禁
  (ruff 增量 lint + kb lint/index --check 双域 + 全量 pytest) PASS,
  commit a67b883 推送 GitHub+Gitee 双远端成功, 未使用 `PREPUSH_SKIP`。

## 适用边界与反例

- 适用于一切"配置解析优先级(环境变量>文件)"型被测函数; 不限 pytest
  (任何有环境注入能力的测试框架同理)。
- 若被测函数本就**应当**优先读环境变量且用例就是要测该优先级, 则用
  `monkeypatch.setenv` 显式设定而非 delenv——关键是**显式**, 不是依赖机器状态。
- 门禁逃生口(如 `PREPUSH_SKIP=1`)只该用于门禁自身故障, 用它绕过真实测试失败
  会把可根治的环境泄漏长期留在仓里。
