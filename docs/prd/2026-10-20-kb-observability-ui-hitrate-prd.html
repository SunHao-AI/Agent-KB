1. 背景与目标

现状。Agent-KB 已具备"检索埋点 → JSONL trace → spider 转换器"的离线链路： kb trace export --format spider 把一次检索导出为 prompt-spider-ui 回放文件， 人工导入后观看动画。但这条链路今天是断的、静默的、无数字的：

  • 无指标可见性：知识库对 agent 到底"帮了多少忙"（命中率、被消费率、省了多少 token）没有任何数字出口。项目的核心价值主张（低 token、三级披露、越用越准）不可证明。
  • 无实时性：回放必须"检索完 → 导出 → 导入 → 播放"，agent 正在干活时观众看不到。prompt-spider-ui 自身已提供 MCP 实时会话（spider_create_session / spider_update_events，支持 follow_live 跟随），但本项目尚未接入；spec §9 也把"实时直播"列为挂账。
  • 命中率机制薄弱：[search.py](file:///d:/Workplace/Agent-KB/src/kb/search.py) 对 title+tags+summary 拼接文本做整 token 小写 find + AND——中文连写（"推流死锁"）、正文专名（"PermissionError"）、同义词（授权/license）三类查询系统性零命中；命中后无排序，limit 截断等于抽签；零命中返回裸 []，agent 直接得出"库里没有"的错误结论。
  • 观测地基已塌：traces/ 被 gitignore，开关 .kb-trace 是本机临时文件，数据已两次丢失（139 行首日数据）。任何指标与实时展示都以"trace 持续存活"为硬前提。

产品决策。沿 spec 已评审的"数据先行、渲染可插拔"三层架构，做五件事： ① 把 trace 从临时物变成持久数据；② 新增观测面板，采用客户端 / 服务端架构：观测服务端（kb serve）是唯一的聚合与推送点，浏览器瘦客户端（kb web）支持单项目 / 多项目联邦两种视图，动画层复用 prompt-spider 视觉语言；③ 按同类项目共识（多信号打分 + 排名融合 + 时效加权）重构检索匹配与排序；④ source（知识来源）升为一等字段，贯穿 trace / 指标 / 路由 / 面板；⑤ 建立知识源连接器（检索联邦）框架：本地 git 知识层之外，TencentDB-Agent-Memory 为默认首个外接源，Notion / 飞书 / 图数据库按统一契约可插拔。

部署与使用模型（v1.1 明确）。

  • 一套系统服务 N 个项目：各业务仓经 submodule（.agent-kb/）+ 项目内 .mcp.json 接入同一套 kb MCP；项目自有知识在 docs/kb/，通用知识在 .agent-kb/kb/（既有双层模型不变）。
  • 观测面 = 客户端/服务端：trace 与各知识源状态汇聚在 Agent-KB 侧的观测服务端（kb serve，唯一事实视图聚合点）；用户在任意项目目录跑 kb web 打开瘦客户端（未检测到服务时自动代拉起），默认进入单项目视图（本项目），可切换多项目联邦视图（结合 TDBM 等外接源状态，跨项目对比 + 按源分层）。客户端不含业务逻辑，所有口径由服务端计算。服务端两种部署形态兼容：单人态（本机自动拉起，默认）与团队常开态（常开主机 + 令牌 + 实时 ingest，FR-2.5）。
  • 知识源可联邦扩展：检索面从"本地双层"扩为"本地双层 + N 个外接源"，外接源命中带来源标识进入同一观测面——"知识库帮了多少"的口径从本地库扩展到全部知识源。

预期可观察结果。

  1. 任何人打开面板即可看到：总检索数、命中率、零命中榜、被消费率、估算节省 token，并可按仓 / 时间筛选。
  2. agent 调 kb_search 时，面板在秒级延迟内出现该次检索的命中动画与逐条分流（项目层命中 / 通用层命中 / 已读消费）。
  3. 已知零命中查询类型（中文连写、正文专名、同义词、长查询）转为可命中，且 top-K 由相关性排序决定；零命中时返回死因与改写建议而非空数组。
  4. 业务开发者在项目目录一条命令打开面板，默认看到"本项目"的命中率与实时命中流，一键切到多项目联邦视图对比所有项目与外接源；外接源（默认 TDBM）的命中同样出现在实时流与指标中，且明确标注来源。

2. 竞品分析与设计启示

对市面同类"agent 记忆/知识库"项目的检索与展示设计做了对照，结论按"是否适配本项目约束（197→未来千级条目、纯 Python 零外部索引依赖、git 为事实源）"过滤后列出：

项目可借鉴设计对本项目的适配判断
Mem0 V3 多信号并行检索：semantic + BM25 + entity 三路打分融合为单一分数；实体层从记忆中自动抽取，检索时Boost 共享实体的结果。 ✅ "多信号融合"思想采纳。entity 信号映射为"正文派生 keywords 入匹配面"（报错串/函数名/配置键正是 agent 最自然的查询词）；semantic 向量路不采纳（违背零依赖约束，197 条规模 BM25-lite 足够）。来源 mem0 v3 迁移文档
mind-mem BM25 + 向量双路 RRF（Reciprocal Rank Fusion, k=60）按排名融合；向量可选，纯 BM25 开箱即用。 ✅ 采纳"排名融合优于分数融合"，RRF 无需给各信号校准量纲，未来若加语义路可直接插第三路。mind-mem · PyPI
mnemo score = 0.5·relevance + 0.2·recency + 0.3·importance，用时间与重要性修正纯文本相关性。 ✅ recency → 既有条目 updated 字段；importance → confidence（verified>probable）。两信号在 index.jsonl 现成可取，零 schema 变更。mnemo search 文档
Zep / Graphiti 时序知识图谱 + 混合检索（语义/BM25/图遍历），强调知识有效期与失效边。 ⚠️ 图谱路线不采纳（重依赖、与 git-Markdown 事实源冲突）；但"知识有生命周期"与本项目 review_by / superseded 机制同构——已具备，纳入排序信号即可（deprecated/superseded 降权）。
prompt-spider-ui MCP 实时会话：create_session → update_events（同 ID 更新状态）→ complete；浏览器 follow_live 跟随，暂停/拖轴不阻塞后台接收；会话内存态、上限 20 会话/万事件。 ✅ 实时展示优先走它的 MCP 工具面或复用其回放引擎（本项目转换器契约已真机校准）；其"会话内存态、需主动导出"的短板反证本项目必须由 trace JSONL 做持久层，UI 只做渲染。Kirito14IT/prompt-spider-ui
TencentDB-Agent-Memory
（工作区内，默认外接源）		 L0–L3 分层记忆（对话→提炼→场景→人设）；召回分层：L2/L3 快速进语境，需要事实时经 BM25+向量+RRF 回 L1/L0；结果受条数、字符预算、超时三重限制；记忆资产与 Agent 框架解耦、Team 内共享；开放 Memory Core / Memory Knowledge / Proxy v3 API（OpenAPI）。 ✅ 作为默认首个外接知识源经 OpenAPI 接入联邦检索。两个直接借鉴：① "结果受字符预算与超时限制"→ 外接源命中必须带预算闸门，防止外部大结果反噬上下文（这与本项目低 token 主张同源）；② 其"分层召回"与本项目"三级披露"同构，L2 摘要先行 / L3 按需全文的读取契约一致，外接源按同一契约返回。
共识提炼（决定本文 FR 走向）： ① 命中率 = 匹配面（查得到）× 排序（排得前）× 反馈（查不到时能自救），三者缺一其余被稀释； ② 多信号加权/排名融合是行业主流，且在千级条目规模不需要向量也能拿到大部分收益； ③ 时效与置信度是一等排序信号，不是过滤参数； ④ 展示层的价值在"持续可看 + 实时可看"，离线导出只是分享态。

3. 范围

3.1 P0 旅程（最小完整闭环）

  • 进入条件：trace 开关开启（默认策略见 FR-1.1），业务开发者在项目目录启动 kb web。
  • P0 动作：trace 持久化含 source/caller 字段（FR-1）→ 面板项目视角看板与实时流（FR-2 + FR-5）→ 检索排序与死因透传（FR-3）→ MCP 返回契约压缩（FR-4）。
  • 完成证据：观众在面板看到本次检索的命中分流动画；看板命中率/节省 token 数字随检索变化且可区分"仅本项目 / 全局"；推流死锁、PermissionError、授权台账 三类历史零命中查询转为命中且排位可解释。
  • 恢复路径：trace 目录缺失/为空 → 面板显示开启引导而非报错（沿用 spec §5 行为）；UI 进程退出绝不影响检索主链路（埋点失败静默红线不变）。

3.2 P1 支持项

  • 中文 2-gram 覆盖率匹配、正文 keywords 入匹配面、aliases 同义词表（FR-3）。
  • 零命中周报（kb stat --zero-hit-report）与回填消化率。
  • prompt-spider MCP 桥接（agent 侧主动上报的"直播态"，FR-2.4）。
  • 知识源连接器框架 + TDBM 默认连接器（FR-6）：统一 SourceConnector 契约、TDBM v3 API 接入、外接源命中进同一 trace/指标/路由观测面。
  • 多项目"发起项目识别"增强：caller 自动识别为项目身份（FR-5.1，P0 用 caller_repo 已够用，识别健壮性属 P1）。

3.3 明确排除

  • 向量嵌入 / 外部搜索引擎 / 知识图谱组件进入本地检索内核（与 git+Markdown 事实源、零依赖约束冲突；但外接源侧允许自带向量/图谱能力，经连接器契约以"摘要先行"方式接入——本项目内核不感知其实现）。未来若加语义路经 RRF 插第三口的升级路径保留。
  • Notion / 飞书 / 图数据库连接器实例（P2 挂账：本版只冻结 SourceConnector 契约并验证"两个异构源可插"，具体连接器待各自鉴权与配额方案评审；契约设计见 FR-6.2，竞品映射见 §2）。
  • 外接源写回（kb_create/kb_update 目标仍只有本地 git 知识层；外接源本版只读——写路径涉及跨系统事实源冲突，独立评审）。
  • 多用户鉴权、多团队空间（roadmap B4 触发器制，未触发；连接器凭据管理见 §5 隐私边界）。
  • 修改 prompt-spider-ui / TDBM 两仓代码（保持只读外件，仅消费其格式与 API 面）。

4. 功能需求

M1 · 观测数据地基 P0

FR-1.1 trace 持久化策略

目的：结束"数据已两次丢失"，指标与实时展示都读同一份持久 trace。

规则：

项决策

M2 · 观测面板：客户端 / 服务端 P0

FR-2.1 架构：观测服务端（kb serve）+ 瘦客户端（kb web）

目的：trace 是集中事实源，指标口径必须只算一次；多项目/多源联邦视图需要跨 caller、跨源的聚合点。这两件事都指向同一个角色——观测服务端。客户端退化为纯视图（渲染 + 交互 + 订阅），零业务逻辑。

角色命令职责约束
观测服务端 kb serve [--port 4320] [--bind 127.0.0.1|0.0.0.0] [--token …]（Agent-KB 仓根；kb web 未检测到存活服务时自动代拉起，部署形态见 FR-2.5） 监听 traces/*.jsonl 增量 → 维护按 caller×source×日的聚合缓存；对外 REST（历史/榜单/KPI）+ SSE（实时事件）；FR-1.2 指标口径的唯一实现；知识源健康态汇总；团队模式下提供 trace ingest 上报口（FR-2.5）。 不写知识内容与门禁面（trace 追加例外，见 FR-2.5）；单机模式仅监听 127.0.0.1，团队模式显式开绑定+令牌；聚合故障/未启动不得影响检索与埋点落盘（读侧与写侧解耦，trace 落盘即事实源成立）。
瘦客户端 kb web [--project X | --all] [--serve-url …]（任意项目目录） 打开浏览器连到服务端；解析当前目录推断项目身份 → 默认单项目视图；提供单项目/多项目联邦切换、时间窗、source 筛选、实时流订阅、动画态入口。 无构建步骤、无本地状态事实（刷新即重建）；服务发现链与降级行为见 FR-2.5（单人态自动代拉起；团队态不可达降级本机+横幅明示），任何情况下不显示脏数据、不把"连不上"演成"没数据"。

视图参数化：单项目 = 服务端查询参数 caller=X；联邦 = caller=* + 按 caller 分组；按源 = source=…。客户端只是参数组合的呈现，新增视图不改服务端。

FR-2.5 部署形态：单人默认态 ⟶ 团队常开态（同一套 C/S，兼容升级）

决策（用户定稿）：kb serve 支持团队常开；kb web 自动代拉起 serve；两种形态共用同一代码与协议，差别只在连接地址的发现方式与访问控制，单人→团队是配置升级，不是架构切换。

单人态（默认，开箱即用）团队常开态（可选启用）
拓扑每人本机：kb web 自动拉起本机 kb serve（127.0.0.1），看自己 clone 的 Agent-KB 数据。一台常开主机（或容器）跑 kb serve，绑定 0.0.0.0:4320；成员浏览器直接访问 http://<host>:4320，或本机 kb web 指向远端。
kb web 行为发现链：本机端口探活 → 存活则直连；不通 → 静默代拉起本机 serve（用户零感知）→ 打开浏览器。代拉起进程随最后一个客户端退出后空闲超时自杀（默认 [TBD: 15min]），不残留。发现链第一步改为读配置的 serve_url（项目 .mcp.json 或用户级 ~/.kb/config）→ 可达则连团队服务端并提示"已连团队实例"；不可达 → 降级到单人态（本机代拉起）+ 顶部横幅明示"团队实例不可达，当前为本地数据视图"。禁止静默把"团队不可达"演成"没有数据"。
数据汇聚trace 落各人本地 Agent-KB 仓根（git 提交汇聚，FR-1.1）。两条汇聚通道并存：① git 汇聚（权威事实源，不变）；② ingest 上报口——业务机 kb 埋点在 trace 落盘之后尽力 POST 到团队 serve（异步、失败静默、不重试超过 [TBD: 1 次]），让"正在发生"的检索秒级出现在团队看板，不必等一次 git push。git 是账本，ingest 是直播，冲突以 trace_id 幂等去重。
访问控制127.0.0.1，无鉴权（本机即边界）。令牌门：kb serve --token 或 KB_SERVE_TOKEN；无令牌访问 REST/SSE/页面一律 401 提示页。令牌只分"能不能看"，不做行级权限（trace 敏感度已论证= index 级）。角色差异化：--read-only-federation 可关"全局联邦视图"只放单项目视图（给外部协作者）是否有此场景待确认。
写面两态一致：serve 永不写知识内容与门禁面；团队态唯一新增写是 ingest 追加 trace（幂等、schema 校验、正文键名拒收——红线不变）。
常开保障不适用（按需拉起）。提供 kb serve --install-autostart（Windows 计划任务 / systemd 单元）+ 健康检查端点 /healthz；崩溃重启由系统服务管理器负责，kb 不自造守护。

口径一致性：团队态看板数字可能短暂大于 git 事实源（ingest 先到、commit 后到），属预期；每个 KPI 悬浮标注数据水位（"含 N 条未入库实时上报"）。禁止两态出现两套指标实现——仍是 FR-1.2 唯一口径。

令牌分发配置示例（团队常开态标准流程）

角色与顺序：① 维护者在常开主机启动带令牌的 serve → ② 令牌随接入指引分发（推荐经 kb init 落盘 ~/.kb/config，手工改文件为兜底）→ ③ 成员业务仓只需在 .mcp.json 声明 serve_url，凭据不落在项目仓（防止入库泄露）。

① 常开主机（管理员，一次性） kb serve --bind 0.0.0.0 --port 4320 --token <随机 32 位> --install-autostart # 令牌也可经环境变量注入: setx KB_SERVE_TOKEN <随机 32 位> # --bind 非 127.0.0.1 且无令牌 → serve 拒绝启动（红线，§5 服务边界） ② 成员机（一次性，推荐经 kb init 自动写入） kb init --repo docs --serve-url http://kb.internal:4320 --token <令牌> # 落盘用户级配置(不入库): ~/.kb/config.toml # [serve] # url = "http://kb.internal:4320" # token = "<令牌>" # 仅用户级文件; 项目仓永不出现 ③ 业务仓 .mcp.json（入库安全，只有地址没有凭据） { "mcpServers": { "kb": { "command": "<venv>/python", "args": ["-m","kb.mcp","--repo","docs"], "env": { "KB_TRACE": "1", "KB_INGEST_URL": "http://kb.internal:4320" } # KB_INGEST_TOKEN 不进这里——埋点上报从 ~/.kb/config.toml 读令牌 }}} ④ 成员浏览器: 项目目录 `kb web` → 发现链读 ~/.kb/config.toml → 带 Bearer 头连团队实例; 不可达 → 降级本机 serve + 横幅明示

安全边界：令牌只分"能不能看/能不能 ingest"；轮换暂不支持（离职收权靠重发新令牌重启 serve，见 §7.2 开放问题 4）。

验收：① 全新机器直接 kb web：无 serve 也能开箱看本地数据（代拉起生效），退出后 serve 超时自杀；② 配置 serve_url 指向团队实例：成员 B 浏览器无本机 Agent-KB 完整数据也能看全团队联邦视图；③ 拔掉团队实例网线：B 的 kb web 降级本机视图且横幅可见；④ 无令牌访问团队实例 REST → 401。

FR-2.2 统计看板（首屏，两种视图共用组件）

目的：一屏回答"这个知识库（对某项目 / 对全部项目）有没有用、帮了多少"。

布局：顶部视图切换（单项目 ⟷ 多项目联邦）+ 时间窗（7d/30d/全部）+ source 筛选；KPI 卡片区（命中率 / 检索数 / 消费率 / 估算节省 token / 知识库自身开销）；中部两张榜单（热门被消费条目、零命中 query 榜）；下部检索流时间线。联邦视图下 KPI 卡叠加"按 caller 迷你分布条"、榜单变"项目矩阵 + 按源堆叠条"（细节见 FR-5）。

FR-2.3 实时命中流（P0）+ 蜘蛛动画（P1 视觉层）

蜘蛛动画（P1）：单条 trace 点开 → 进入全屏动画态，复用 prompt-spider 视觉语言与三分支分流。实现路线二选一（评审定）：a) 内嵌 prompt-spider-ui 回放页，面板把 trace 现转为 record 经 URL/iframe 传入（转换函数已有，spider_export.to_record 抽为进程内复用）；b) 面板原生 Canvas 简化动画。推荐 a：零前端重做、格式已真机校准。

规则：暂停/筛选只改观看位置不丢事件（follow_live 语义）；事件保留窗 [TBD: 默认当日]；页面切后台恢复后自动追赶最新。

M3 · 检索命中率提升 P0 / P1

FR-3.1 多信号排序（P0）

触发：evaluate() 命中集合产出后、limit 截断前。竞品共识（mnemo 加权式 + RRF 排名思想）落地为纯函数打分：

信号取值权重建议 评审定
字段权重title > tags > keywords(P1) > summary，取命中 span 的最高字段权重5 / 3 / 2 / 1
命中密度命中 token 数占比 × span 密度（惩罚"碰巧沾一个词"）×1.0 归一
置信度verified 1.0 / probable 0.8（speculative 已被门禁挡在检索外）×0.2 加分项
时效exp(-Δupdated/90d)，deprecated/superseded ×0.3×0.1 加分项

结果：matched.rank 改由分数决定；trace 与 MCP 返回携带 rank 与分数（可解释性："为什么这条排第一"）。双层合并策略同步调整：各层先内部排序再按层优先级取数（层序仍项目层优先，spec §7 不破）。

验收：查询「授权」首位为标题命中条目；既有 206 测试全绿 + 排序回归用例。

FR-3.2 零命中死因透传（P0）

MCP kb_search 零命中时不再返回 []，返回结构化对象：

  • hits: [] + hint：死因计数（scanned / 死于过滤器 N / 死于词匹配 N）+ 建议（更短单 token、该域可用 tags）；
  • 追加 suggest：difflib 对 title 分词的近似词（"你是想查'推流卡顿'？"），最多 3 个。

命中时返回结构不变（数组），保持现有调用零破坏。suggest 词面进入 trace 事件，供面板与零命中榜关联"已消化"判定。

FR-3.3 CJK 2-gram 覆盖率匹配（P1，先补 spec 再动）

查询侧 CJK 连续段切 2-gram（"推流死锁"→{推流,流死,死锁}），按覆盖率 ≥0.6 判命中（跨词碎词命中不了属预期）；西文保持既有空白分词 AND。等价于用零依赖方式拿到"轻量分词"的大部分收益；Mem0 式 entity 信号的本地化替代。hit_spans 语义同步进 trace spec（schema 版本 +1）。

FR-3.4 匹配面扩展：keywords + aliases（P1/P2）

  • keywords（P1）：kb index 从正文派生 ≤20 词/条（代码围栏标识符 + H2 段名 + 高信息 token），入 index 并入匹配面——对应竞品 entity 信号，解决 PermissionError 类报错串零命中。索引每条约 +200B，可接受。
  • aliases（P2）：front-matter 可选 aliases: []（授权/license 中英对照），schema 走 taxonomy.yaml 唯一事实源老规矩，index 与查询双侧展开。

FR-3.5 零命中反馈回路（P1）

trace 持久化（FR-1.1）后：每周跑 kb trace list --zero-hit → 高频词逐条消化（补 tags / 改 summary / 立新条 / 加 alias）→ kb stat --zero-hit-report 输出消化率 → 面板展示"已消化 ✅"。这是唯一让命中率随使用时间单调上升的机制；其余各项是一次性修复。

M4 · Agent 侧返回契约 P0

FR-4.1 MCP 返回压缩 + 排序后可见信息

  • compact 序列化（去缩进）+ 默认字段裁剪：保留 id/title/type/domain/scope/confidence/summary/path，新增 hit_fields（比 summary 更快回答"为什么命中"）；status/severity/updated 仅在显式过滤时返回。单次返回 5518 字 → 约 3.5–3.9k 字。
  • 排序上线后 MCP 默认 limit 10 → 5（累计 token -60~65%）。硬依赖：排序先行，否则只是提高抽签率。
  • 工具描述补检索姿势三段话（分词规则、中文短词建议、死因字段读法），约 150 字常驻，替代"靠踩坑传递"的循环依赖。

M5 · 单项目 / 多项目联邦视图 P0 单项目 P1 联邦

FR-5.1 项目身份识别与单项目视图（P0）

目的：kb MCP 被多个项目共用（各自 .mcp.json 指向同一套代码），trace 集中落在观测服务端；"我在我的项目里打开 UI，默认只看我的数据"必须由数据模型 + 客户端启动推断保证，而不是靠人记 filter。

项规则
身份字段沿用既有 caller_repo（发起检索的仓目录名小写）作为项目身份唯一口径，不新造概念。MCP 实例启动时已知自身项目名，埋点直接带上，零新增推断成本。
客户端启动推断kb web 在业务项目目录启动时：读项目 .mcp.json / .agent-kb 挂载与目录名，解析出本项目身份 → 打开后默认视图 = caller == 本项目（单项目视图）；在 Agent-KB 仓根启动 → 默认进入多项目联邦视图。显式 --project X / --all 覆盖推断。
识别失败目录名与 trace 中任何 caller 都不匹配 → 顶部横幅明示"当前项目无检索记录（识别为 X）"，并列出已见 caller 供一键切换；禁止静默显示空图让人误判"知识库没用"。
同名冲突不同机器/父目录下同名项目目录会合并计数（caller 口径是目录名）。风险与现有 trace 口径一致，本版接受；若成真痛点再以 repo_path_hash 细分 观察项。

验收：项目 A 与项目 B 各跑 kb_search 后，在 A 目录启动 kb web，看板 KPI、榜单、实时流均只含 A 的记录；点"联邦"可见两项目并按 caller 区分。

FR-5.2 多项目联邦视图（多客户端共用一个服务端）

联邦视图 = 服务端 caller=* 查询 + "项目矩阵"：每项目一行——检索数、命中率、消费率、估算节省 token、最近活跃时间、trace 是否存活（掉线检测：接入但长期零记录 = 开关失效告警，正是 followup T2 问题的看板化）、该项目启用哪些知识源。再叠加知识源维度：按 source 堆叠的命中占比与源健康（tdbm 延迟/成功率等，来自 FR-6 健康探针）——即"项目 × 知识源"双轴矩阵。

价值：把"这套系统值不值"从单项目叙事升级为跨项目 + 跨源证据；服务端单点聚合让任意多个客户端（各项目开发者、维护者）同时连同一 URL 各看各的视图，互不干扰。

验收：两个浏览器分别以 A 目录 / 仓根打开，同一服务端下分别呈现单项目视图与联邦视图；联邦矩阵行数 = 已见 caller 数，含源健康列。

M6 · 知识源连接器（检索联邦）P1 框架+TDBM P2 更多源

FR-6.1 统一概念：source 升为一等字段

今天"来源"只有隐含的两层（项目层/通用层，由目录顺序表达）。接入外部源后，source 必须显式化并贯穿全链路：

载体变化
trace（schema=2）search 事件每层 report 加 source 与 source_kind（local-git | external）；外接源 report 记录 latency_ms、budget_cut（被预算截断数）、error（超时/鉴权失败等）。恒等式扩展为逐源成立。
命中条目返回行携带 source（如 tdbm / notion / local:docs / local:kb）与源内引用句柄（外接源的条目没有本仓 path，用 source://<connector>/<native_id> 统一寻址）。
UI 路由蜘蛛三分支扩展为"路由可配置"：既有 项目层/通用层/已读消费 保留，外接源命中进入新增路由（如"外接·TDBM"独立配色）；"已读消费"仍是跨源覆盖层标记（哪个源的条目被 kb_get 式读过）。spider record 的 routes 本就是 config 字段，扩展合法。
指标FR-1.2 全部口径按 source 维度可分层：外接源命中率、外接源贡献的节省 token、本地 vs 外接的命中占比（面板堆叠条展示）。

FR-6.2 SourceConnector 契约（P1 冻结）

连接器是只读检索适配器，产品行为契约（实现细节由 spec 承接）：

契约面要求
能力申报声明：是否支持自由文本 query / 结构化 filter / 分节读取（section）/ 关联（related）。能力缺失时按"不支持→降级"处理（如只读全文的源，section 读取降级为整篇+预算截断并在 UI 标注）。
返回形态摘要先行：检索命中必须返回 L2 级摘要 + source 内句柄 + 源内相关性序；全文按需二次读取（三级披露跨源一致）。禁止连接器把外部全文塞进检索返回。
预算闸门每源独立：超时上限（默认 [TBD: 建议 800ms]，超时降级为"该源本次不可用"并计入死因）、返回条数上限、字符预算上限。借鉴 TDBM"条数/字符/超时三重限制"——外接源不得反噬本地库的低 token 主张。
优先级与融合本地双层优先（项目层→通用层）取数后，剩余名额给外接源；外接源之间按配置权重 + FR-3.1 打分统一排序 融合细则 spec 阶段定。跨源去重：同一条外部知识被重复命中按 source 句柄折叠。
故障与观测任何源故障（网络/鉴权/超时）静默降级 + trace 记 error，检索永不因外接源失败而失败（与埋点红线同构）；面板按源显示健康态（近 N 次成功率/延迟）。
凭据连接器凭据走本机环境/本地配置，永不入库、永不进 trace（收录红线延伸到连接器）。
配置面项目 .mcp.json 的 kb server args 增加 --sources tdbm 式声明 + kb sources list/status CLI 自检（并入 kb doctor）。

FR-6.3 TDBM 默认连接器（P1）

为什么默认：同为 agent 记忆系统、工作区内已有、开放 v3 OpenAPI（Memory Core / Knowledge）、无额外 SaaS 依赖——是验证契约的最小真实外接源。

  • 映射：TDBM 记忆资产 → 命中条目；其分层召回结果（L2/L3 摘要 + 句柄）→ 摘要先行返回；其 BM25+向量+RRF 黑盒完成，本项目不重复建设，仅做跨源统一排序。
  • 身份传递：检索携带 caller 项目与 agent 身份参数，保证"哪个项目借用了哪些团队记忆"可观测 TDBM 侧 Team/Agent 映射待确认。
  • 验收：项目 agent kb_search 返回中含 source: "tdbm" 命中；面板实时流出现"外接·TDBM"路由卡片；TDBM 服务停机时检索正常、死因区显示"外接源超时"。

5. 共享规则与边界

规则内容
红线不变trace 不含正文（CI 键名校验，团队态 ingest 口同样拒收正文键名）；埋点/UI/观测服务端任何故障不得影响检索主链路（写侧与读侧彻底解耦：kb serve 挂了 trace 照常落盘）；kb serve / kb web 不写知识内容与门禁面（团队态 ingest 追加 trace 为唯一例外，FR-2.5）；prompt-spider-ui / TDBM 两仓只读不改。
指标口径单一所有界面/CLI/报表口径引用 FR-1.2 定义表，且只在观测服务端实现一份，客户端与 stat 命令均消费服务端结果；"节省 token"永远带"估算"标识。
服务边界默认单机态：仅监听 127.0.0.1，无鉴权（本机即边界）。团队常开态（FR-2.5）为显式启用：绑定非本机地址必须同时带令牌，缺令牌则 serve 拒绝启动（防止无意裸奔）；ingest 口同令牌门。用户/角色级权限、OAuth 等仍留给 roadmap B4。kb web 代拉起 serve 时恒用单机参数。
隐私边界trace 含 query 原文与 caller 仓名（与 index 同敏感度，FR-1.1 已论证）；query 若命中敏感词面处理策略 TBD：是否需要脱敏白名单。
兼容与迁移trace schema 版本化（现 schema=1；rank/score/returned_chars/suggest 字段 → schema=2），reader 对低版本容错、高版本跳过（既有策略）。MCP 命中态返回结构不变，零命中从数组变对象是行为变更，需在工具描述与 AGENTS.md 同步声明。
性能地板197→5k 条规模 O(N) 全扫 + 打分 <10ms 量级成立；面板聚合在前端做（trace 行数年级仍 <10 万行）；超限再议增量聚合。

7. 已定决策与开放问题

7.1 已定决策（用户确认，2026-10-20）

  • 观测面采用 C/S 架构；UI 支持单项目 / 多项目联邦两视图（v1.2）。
  • kb serve 升级团队常开模式，且与单人态兼容——同一协议与代码，配置升级而非架构切换（FR-2.5，v1.3）。
  • kb web 自动代拉起 serve：单人态默认行为，代拉起进程空闲超时自杀；团队态按 serve_url 发现、不可达降级本机并横幅明示（FR-2.5）。
  • 知识源联邦：TDBM 为默认首个外接源；Notion / 飞书 / 图数据库按 SourceConnector 契约挂账 P2（FR-6）。

7.2 开放问题（仅存影响决策项）

  1. trace 全量入 git vs 每月归档仓（本 PRD 推荐全量入 git，需确认仓库体积容忍度与 CI 索引重建策略）。团队常开态下 git 仍是权威账本，此问题不因 FR-2.5 消失。
  2. "估算节省 token" 的字符→token 系数与展示措辞（是否直接展示字符数代替）。
  3. 排序权重数值（5/3/2/1 + 0.2/0.1 加分）是否直接采用后以 trace 回放验收调参。
