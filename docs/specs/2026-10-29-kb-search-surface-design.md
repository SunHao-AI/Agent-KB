# KB 检索面扩面(keywords 按段分桶 + sections 字段) 设计

- 日期: 2026-10-29
- 状态: 已评审通过 (2026-10-29, 用户确认方案 2; spec 落盘于项目既有 `docs/specs/` 目录)
- 上游: `docs/specs/2026-10-12-agent-kb-design.md` FR-3.4(索引派生)、`2026-10-13-agent-kb-p1-design.md` §4(双层检索与索引生成物)
- 触发: flysee 项目库 `kb-20261012-64e8` 追加"新发现"后按红线 #3 检索去重, 零命中

---

## 1. 背景与目标

现状: `kb search` 的匹配面只有 `title + tags + keywords + summary` 四个字段(`search.py::_parts`), 其中
`keywords` 由正文派生但**硬截断前 20 词**(`index.py::_KEYWORDS_CAP`), `summary` 是**正文首个内容块前 120 字**
(`entry.py::summary`)。两者都不随"向既有条目追加新病灶面"而增长。

后果: 门控红线 #3 要求"沉淀前必须 `kb search` 去重; 命中既有条目则更新追加『新发现』, 不新建"。而追加进去的
内容**检索不到** —— 门控强制写入的路径, 恰好让下一个人搜不到已有答案, 于是重复沉淀。去重机制在它自己推荐的
写入路径上失效。

实测证据(2026-10-29, flysee 项目库):

| 通道 | 机制 | 实测 |
| --- | --- | --- |
| A. keywords 截断 + 顺序偏置 | cap=20 按"围栏→行内码→H2 名→段落"顺序取, 先到先占满配额 | 该条目追加约 1400 字(含 `zone`/`resolve`/`172.19.0.2`)后重建索引, `keywords` 字段**一字未变**; 全库 577 条中 **447 条(77%)被截断**, p50=31 / p90=55 / max=106 |
| B. 正文不在匹配面 | `_parts` 不含正文; `summary` 仅首块 | 追加后 `漂移` / `IP 漂移` / `502` 全 MISS, 而老内容词 `nginx resolver rewrite` HIT |

**关键结论**: 单修 cap 不够。`_IDENT_RE = [A-Za-z_$][\w$.]{3,}` 结构上排斥纯数字(`502` 永不入 keywords),
`_is_informative` 又排除纯小写散文词, 中文词只能靠正文的 CJK 2-gram 兜底 —— 正文不在面即无解。**通道 B 是主因**。

影响面旁证: `traces/` 累计 432 条 search 记录(289 个不同 query)中 **274 条零命中**。该比率含 QA 走查与探针
故意构造的负例, 不能当作缺陷的直接度量, 但方向上与"匹配面过窄"一致; 这批记录同时是 §6.5 的回归语料。

目标: 让"向既有条目追加的新病灶面"可被检索命中, 同时守住 L2 人读面(INDEX.md)外观与 L3 token 成本不变。

## 2. 范围

**In scope**
- keywords 派生改为**按 H2 段分桶**, 消除"前段占满配额"的顺序偏置
- 新增 `sections` 匹配字段(每段首句摘要拼接), 打开通道 B
- `kb index` 重建全部既有索引; `kb_search`(MCP)自动受益(读同一 `index.jsonl`, 无需改 mcp.py)
- 回归测试 + 噪音准入门槛(见 §6)
- 使用侧兜底: AGENTS.md 沉淀协议补"追加新发现必须同步补 tags"

**Out of scope**
- 分词器 / 向量检索 / `aliases` 双侧展开(P3 挂账, 本次实测显示"整串查询词不在 tags 即 MISS"确是其代价)
- `summary` 语义与外观变更(被 INDEX.md 与 `kb stat --needs-scope` 消费, 明确不动)
- `dedup_key` 算法(仅标题归一化 sha256, 本次未受影响, 但"追加不改标题"同样绕过它 —— 挂账)
- 四个业务仓接入 `kb index --check` 门禁(独立事项)

## 3. 设计原则:新增字段,不改既有语义

曾考虑直接改 `Entry.summary()`, 但 `summary` 同时是**匹配字段**与**展示字段**:
`index.py::_md` 把它渲染进 INDEX.md 每一行, `query.py::needs_scope` 用它做待审清单摘要。改它会让 INDEX.md
每行从 ~120 字膨胀到 ~400 字, 污染 L2 人读面。

故: `summary` 完全不动, 新增独立字段 `sections` 专供匹配。纯增量、向后兼容 —— 沿用 `keywords` 已有套路
(`search.py` 对老索引行 `rec.get("keywords") or []`), 老行缺 `sections` 自动当空, 不报错。

## 4. 改动明细

### 4.1 `index.py` — keywords 按 H2 段分桶

```python
_SECTION_KW_CAP = 8    # 每个 H2 段的 keywords 配额
_KEYWORDS_CAP = 64     # 全局安全阀(原 20)
```

`derive_keywords(body)` 改为: 对 `dedup.h2_sections(entry)` 的**每一段**各跑一遍现有四级派生(围栏 → 行内码
→ H2 名 → 段落), 每段取 ≤ 8 词, 跨段保序去重, 末尾封顶 64。解析器复用 `dedup.h2_sections()`, 不新写。
签名随之从 `derive_keywords(body: str)` 改为接收已解析的段落列表(或整 `Entry`), 因其需段边界。

**不设"无 H2 段"退化分支**: 实测全库 577 条(四仓 + Agent-KB)**全部含 H2 段, 0 例外**, 六段式骨架由
`kb lint` 强制。该分支属为不会发生的场景加防护, 改为用 §6.0 的回归测试守住同一风险(改动后任何条目
keywords 不得为空)—— 测试比运行时分支更合适, 且能同时抓住"分桶逻辑写错导致静默清零"这类真错。

**不变项**: `_IDENT_RE` / `_INLINE_CODE_RE` / `_is_informative` 与 `_STOP_IDENT` 一律不动 —— keywords 的
"只收标识符, 不收正文句子"定位保留, 故本项**零误命中增量**。

### 4.2 `entry.py` — 新增 `sections_text(limit=60)`

每个 H2 段取**首句**: 跳过围栏后的正文, 取首个非空行, 在 `。！？` / `.!?` / 换行处截断(保留终止符),
再按 `limit=60` 字二次截断; 各段结果以空格拼接。六段式骨架下"每段首句"天然就是该病灶面的主旨句,
是有界且高信息密度的匹配面。

实测锚点: 本次追加段的首句「新发现(2026-10-29): 同一机制的第二病灶面 —— 启动期解析成功、但上游 IP 事后漂移」
正落在此面内, 进面后 `漂移` / `IP 漂移` 可搜。

### 4.3 `index.py::_records` + `search.py`

- `_records`: 记录加 `"sections": e.sections_text()`
- `_parts`: 追加 `("sections", rec.get("sections") or "")`
- `_FIELD_WEIGHT`: `"sections": 1.5` —— 高于 `summary`(1.0, 仅首段), 低于 `keywords`(2.0, 高信号标识符)

排序、`_score`、`_token_spans`(含 CJK 2-gram)、`_hit_fields` 全部零改动, 新字段自动获得现有 CJK 分词能力。

### 4.4 索引再生成

Agent-KB 仓 `kb/` 与四个业务仓 `docs/kb/` 全量 `kb index`(生成物, 不可手改)。MCP 层读同一 `index.jsonl`,
无需改 `mcp.py`。

## 5. 成本

| 项 | 预估 | **实测(2026-10-29)** |
| --- | --- | --- |
| Agent-KB 主仓 `kb/index.jsonl` | — | **176.8 KB → 302.5 KB(+71%)** |
| 577 条 keywords 合计 | 145,822 B → ~247 KB | keywords 分桶 + sections 合计约 +126 KB |
| 四业务仓 `docs/kb/index.jsonl` | — | 见 §5.2(业务仓重建后回填) |

仍是数百 KB 量级。检索侧只回元数据 + `summary`(**`sections` 不进返回值**), 故 **Agent L3 token 零增长**。

### 5.1 噪音实测(spec §6.5 判据 + 补充的决策相关指标)

对照组: Task 1 快照的旧生成物(keywords cap=20、无 sections)。语料: `traces/*.jsonl` 的
**292 个真实历史 query**(非人工构造)。

| 指标 | old | new |
| --- | --- | --- |
| 总命中条次 | 199 | **363**(+82%) |
| 零命中 query 数 | 247 | **238** |
| `hit_fields` 仅含 `sections` 的命中 | — | 106(**29.2%**,门槛 30% → PASS,余量仅 0.8pt) |
| 前 8 名**被挤出**的位次数 | — | **10**(303 query) |
| 前 8 名**新挤入**的位次数 | — | **114** |

**判据有效性的自我批评(重要)**: 29.2% 看着逼近红线, 但该指标把"原本不可见的内容现在可见"
也计为噪音——那正是本设计的**目的**(例: `授权` 命中 `kb-20261013-3b55`, 旧索引完全搜不到)。
按 query 词数分解更清楚: 单词 query 的 sections-only 占比 32%, 二词 6%, 三词及以上 0%——
噪音集中在宽泛单词查询, 而这类查询的排序本就是噪音区。

**真正该守的是"旧答案被新命中挤出前列"**(agent 只消费前 limit 条), 实测 303 个 query 仅丢
10 个位次、换回 114 个, 净效应强正向 → **保留 sections 面**。

权重敏感性不作数: 1.5 与 1.0 对"首条仅靠 sections 命中"的计数无差异(均 32/120), 探针过粗
(未计入 confidence/recency), 不足以支撑调权结论。若后续要调 `sections` 权重, 须用
`kb search` 端到端排序对比重做。

**后续动作(挂账)**: 本轮暴露"spec 的验收判据衡量错了东西"。下次改检索面时, 判据应直接写成
**top-N 位次挤出数**, 而不是新增命中的字段构成占比。

## 6. 测试与验收

0. **keywords 非空守护**(替代运行时退化分支): 对全库语料断言改动后**没有任何条目 keywords 变成空列表** —— 同时
   覆盖"无 H2 段"假设失效与"分桶逻辑写错导致静默清零"两类风险
1. **段分桶不被前段占满**(直接复刻本次故障): 前段塞 30 个标识符, 断言后段的 `zone` / `resolve` 仍在 keywords 内
2. **老索引行缺 `sections` 不报错**: 兼容既有生成物
3. **INDEX.md 行宽不变**: 断言渲染结果不含 `sections` 内容(守住 L2 人读面)
4. **端到端可搜**: 用真实条目断言 `漂移` / `zone` 类查询命中 `kb-20261012-64e8`
5. **噪音准入门槛(§7 回退依据, 判据可量化)**: 固定一组既有 query(从 `traces/` 历史 query 取, 不足则手写 20 条
   覆盖中英文), 对全库跑改动前 / 改动后, 记录三个数: 总命中条数、零命中 query 数、结果中 `hit_fields` **仅含
   `sections`** 的条目数。门槛: **第 3 项 > 总命中的 30%** 判定噪音失控 → 砍掉 §4.2 只保留 §4.1(标号顺延不影响
   其余条目独立性)

## 7. 风险与回退

- **风险 1: CJK 误命中上升**(唯一实质风险, 来自 `sections`)。缓解: 权重 1.5 + hay 有界(≤ 段数 × 60 字)+ §6.5 门槛。
  回退: 撤 §4.2/§4.3 中 sections 相关两处, §4.1 独立成立, 收益(标识符可搜)保留。
- **风险 2: 索引膨胀**影响 `kb index --check` 与 git diff 噪音。缓解: cap=64 全局阀; 实测上界 ~430 KB 可接受。
- **风险 3: 权重需调**。`sections` 初始 1.5 为经验值, 若顶掉 title/tags 命中则下调至 1.0。
- **风险 4: 分桶后 keywords 数量上升**改变既有 query 排序, 可能把原本靠后的条目顶到前面。属预期收益, 但由 §6.5
  的对比数据一并观察, 若排序漂移过大则下调 `_KEYWORDS_CAP`(64 → 48)。
- 各项均为**局部回退**, 不涉及数据迁移(`sections` 是生成物字段, 删字段即回退)。

## 8. 使用侧兜底(独立于代码发布)

AGENTS.md 沉淀协议补一条: **向既有条目追加"新发现"时必须同步补 tags**。tags 权重 3.0(最高), 是本次唯一真正
救回检索的手段(`container-ip-drift` 一搜即中), 且对**已 accepted 的存量条目立即生效**, 不依赖代码发布。
