# MCP 传输选 stdio 无鉴权的信任域边界与重开条件

## 背景

Agent-KB 向各业务仓的 agent 暴露知识库读写有两面：`kb` CLI（本机）与 MCP server（agent 会话内）。MCP 传输方式与是否鉴权需要定型。P0/P1 设计期（2026-10-13）的实际场景是：使用方全部为同机开发者及其 agent，`.mcp.json` 里 command 直接拉起本机 venv 内的 `python -m kb.mcp`，无任何远程接入方。

## 候选方案

1. **stdio 无鉴权**：MCP server 由客户端以子进程方式拉起，仅同机可连；访问控制完全交给本机文件系统权限。
2. **HTTP 传输 + token 鉴权**：常驻服务，跨机可连，需引入 token 签发/校验与多租户边界。
3. **stdio + 本地 token**：同机连也要求 token——防护对象（跨机攻击者）根本不经过这条链路。

## 决策

选 1：stdio 无鉴权，与 CLI 同信任域（本机开发者），明确记录为 YAGNI 取舍而非"鉴权做完了"。同时写死重开条件：**出现第一个跨机/多团队远程接入用户时，本决策作废**，必须先补 spec 再实现 HTTP 传输 + token 鉴权（该项已挂 B4 触发器，见 `docs/plans/2026-10-14-roadmap-commercial-launch-and-agent-kb.md`）。

## 理由

- stdio 的生命周期由 MCP 客户端管理，无监听端口，攻击面 = 本机进程面，与直接跑 `kb` CLI 完全一致；加 token 不减少任何本机攻击面（方案 3 被排除的原因）。
- 知识库内容本身无高于代码仓的机密级（红线已禁密钥/凭证入库），鉴权收益低于其运维成本。
- 沉淀门控红线（draft/project/speculative 强制、scope 终审人工）在**进程内代码层**实施，不依赖传输层信任假设——即使未来换 HTTP，红线逻辑可原样复用，本期不因传输选型产生返工。

## 后果

- 正面：零配置接入（`kb init` 生成 `.mcp.json` 即用），无密钥分发/轮换/存储负担。
- 负面：同机上任何能以该用户身份起进程的实体都拥有与开发者等同的库读写面——接受，因为这等同 CLI 的既有信任面。
- 约束性后果：任何远程接入需求都必须先重开本决策（写进 B4 触发器的第一步），不允许"先临时开 HTTP 再补鉴权"。
