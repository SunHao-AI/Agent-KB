# 热端点全量扫追加式 JSONL 履历：随行数线性退化（185ms/请求）——"取最近一条"必须尾扫

## 背景 / 现象

热端点 `_last_sync_at()` 为取"最近一次续约时间"全量扫追加式 JSONL 履历（当时 8376 行逐行 `json.loads`），185ms/请求且随行数线性增长。

## 根因

`backend/api/v1/system.py` 的 `_last_sync_at()` 为了取"最近一次续约时间"，调用 `ledger.read_events(since_seq=0, limit=1_000_000)`——把**整个追加式履历 JSONL（当时 8376 行）逐行 `json.loads` 全量解析**再取最后一条命中项。履历只增不减，成本随行数线性增长；今天 185ms，跑一年就是秒级。容器内分段计时实锤：ledger 全量读 185.5ms vs 尾 seek 5.3ms（35 倍差距）。

## 解决方案

`backend/license/ledger.py` 新增 `last_event_where(events)`——从文件尾按 64KB 块**反向**扫（`_TAIL_CHUNK = 64KB`，上限 `_TAIL_MAX_CHUNKS = 32`），命中即停；块边界残行拼 `leftover`、末行损坏 JSON 静默跳过（追加式文件的常态：写入进程可能在最后一行被截断）。`_last_sync_at()` 改用它，只找 `EV_RENEW_OK / EV_RENEW_FAIL` 两类事件。后端 185ms→**14ms**，浏览器 keep-alive 复测 253ms→**25ms**。回归用例见 `tests/test_license_ledger.py`（含 monkeypatch `_TAIL_CHUNK=256` 强制跨块、追加半行损坏 JSON 两个关键场景）。

## 验证

后端 185ms→**14ms**，浏览器 keep-alive 复测 253ms→**25ms**。回归用例见 `tests/test_license_ledger.py`（含 monkeypatch `_TAIL_CHUNK=256` 强制跨块、追加半行损坏 JSON 两个关键场景）。

## 适用边界

- **追加式日志/履历文件上"取最近 N 条命中"永远不要从头全量解析**。反向块扫（tail-scan）是 O(尾部若干 KB) 常数成本；正向全扫是 O(文件全长)，且追加式文件意味着它单调恶化。

- 反向扫的三个必修边界：① 块首行是被切断的残行（与后块 leftover 拼接或丢弃块首不完整行）；② 末行可能损坏（追加写被截断是常态，须跳过而非抛错）；③ 扫描深度设上限（`_TAIL_MAX_CHUNKS`），找不到就返回 None，防止"事件极老"时退化成全文件反向扫。
热端点的耗时要盯"是否随数据量增长"：单次 185ms 不致命，致命的是它是行数×解析成本的函数；上线时快≠一直快。
