# 超时链预算倒挂：服务端"有界"的 503 迟于浏览器 axios 预算到达，可重试提示变成永远收不到的死信

## 背景 / 现象

D11 把半死 MySQL 从"无限阻塞"修成"30s 有界 + 503 可重试"后，按真实用户路径复测：

```

[probe] status=503 耗时=60.18s   ← 有界, 但已经是上一版的"正确"值

[verdict] FAIL: 60.18s ≥ 浏览器 axios 预算 10s → axios 先 abort,

          后端 503 文案永远不会被看到

```

用户实际看到的是 request.js 兜底的笼统「系统接口请求超时」，而不是「服务暂时不可用（数据库连接异常），请稍后重试」。**错误语义在最后一公里被静默丢弃**：用户不知道该重试还是该报障，运维也没有"数据库异常"这条线索。同域开发环境（直连、DB 健康）100% 不可见。

## 根因

| 层 | 配置值 | 各自理由 |

| --- | --- | --- |

| 浏览器 axios | 10s | "默认值，够用了" |

| nginx `proxy_read_timeout` | 300s | "要容忍 .zapk 分钟级安装" |

| DB read | 30s | "要容忍合法慢批写" |

| `pool_pre_ping` | 开 | "检坏连接更稳" |

`pool_pre_ping` 检出坏连接后会**丢弃并新建连接重试一次**，故半死路径最坏 = **2 × read = 60s**。没有任何一层是错的，但**从外往里没有任何一层为内层的总和留预算**——这类"局部最优、全局倒挂"在超时链上极其常见，且只在故障时暴露。

## 解决方案

**从最外层消费者预算往里推**，令每条失败路径的最坏耗时都留有余量：

```python

# config.py：半死路径 2×read=8s、黑洞 2×connect=4s、池排队 6s，均 < axios 10s

DB_CONNECT_TIMEOUT: int = 2

DB_READ_TIMEOUT: int = 4

DB_WRITE_TIMEOUT: int = 4

DB_POOL_TIMEOUT: int = 6   # 原 10s 正好等于 axios 预算边界, 同样吞掉 503

```

安全性核查（怕误伤合法慢查询）：直连真实 MySQL 逐条计时纯 SQL——`SELECT 1`/`client_config` 单行/suites 分页/model_cache/tasks 分页/`count_active`，**最慢 18ms**，4s 上限宽松 200 倍。`.zapk` 安装的分钟级耗时在**磁盘加解密与模型重加密**，不占单条语句，不受 read_timeout 影响（其预算由 axios/nginx 的 300s 承担）。

复验：pause 注入下真实用户路径 **503 @ 8.22s**（< 10s 预算，用户可见）；`pytest tests/test_config.py` 20 passed、全量 547 passed。

防线固化成断言（数值型不变量唯一可靠守法）：

```python

# tests/test_config.py

BROWSER_REQUEST_BUDGET_S = 10.0   # 与 frontend/src/utils/request.js 手工对齐

for name, worst in (("半死连接", 2 * settings.DB_READ_TIMEOUT),

                    ("握手黑洞", 2 * settings.DB_CONNECT_TIMEOUT),

                    ("池排队", settings.DB_POOL_TIMEOUT)):

    assert worst < BROWSER_REQUEST_BUDGET_S

```

## 验证

本仓 read=30s 的原始理由是安装慢，实测纯 SQL 最慢 18ms、慢的是磁盘加解密（不受 socket 读超时约束）。逐条计时只要 10 行代码，却能把超时值放宽 200 倍的错误理由直接推翻。

## 适用边界

- **超时值必须"从最外层消费者的预算往里推"**，不能"从最慢的合法操作往外推"：先钉住浏览器/调用方预算（本仓 10s），再要求链路上**每一条独立失败路径**的最坏耗时都小于它并留余量。反过来定，故障时的结构化错误永远送不到用户手上。
