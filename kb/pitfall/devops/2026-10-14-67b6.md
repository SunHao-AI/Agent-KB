# 近重条目判了通用却留仓：落位红线把语义中间态打回归属终判

## 背景 / 现象

P2 scope 终审（229 条迁移条目）落地时，4 条 web-frontend 条目（`kb-20261013-b3af` / `9848` / `3e06` / `c831`）判为 `scope: stack` 但因与通用库语义近重而决定不 export（留在项目库）。执行 `kb lint --scope project` 立即报错阻断：`<id>: scope!=project must be promoted to agent-kb`。

## 根因

`scope` 一个字段绑定了三重语义：① 归属判定（提案结论）；② 物理落位（lint 红线：项目库内条目的 scope 必须为 project，通用库内不得有 project——见 `src/kb/lint.py` 落位检查）；③ 标签清理（`set-scope` 副作用清 `needs-scope-review`）。「判定 stack 但物理留仓」让 front-matter 与物理位置矛盾，被一致性红线拦截。语义归属与物理位置没有中间表达（如 `stack-pending`），这是 schema 的有意设计：stack 知识只应存在于通用库单点。

## 解决方案

二选一，禁止中间态：
- 近重不导出 → 改判 `scope: project` 留仓（`kb set-scope <id> project`，语义增量以「本仓特有触发场景」体现在正文）；
- 确要上提 → `set-scope <id> stack` 后紧跟 `kb export --to-repo`，一步完成不留窗口。

## 验证

4 条改判 project 后 `kb lint --scope project --repo docs` rc=0，`kb index --check` 全部 up to date（P2 落地会话 2026-10-14 实测）。

## 适用边界与反例

终审尚未 export 的批量落地窗口内允许短暂 project→stack 中间态，但 commit 前必须 lint 收敛；条目若后续因通用库版本演进而值得独立上提，重新走 set-scope+export 即可，project 留仓不丢信息。
