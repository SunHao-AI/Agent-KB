# 测试合成语料污染观测账本: 读侧按 caller 剔噪而非改写账本

## 背景 / 现象

Agent-KB 观测面板(数据源 = `Agent-KB` 仓 `traces/*.jsonl` 埋点账本)的榜单长期失真:
零消费榜榜首是被反复消费 61 次的 `kb-20261014-e1e1`(conftest `make_entry` 夹具 id),
热门榜/命中率也被同批数据抬高。离线探针实测全账本 1311 条事件中约 25% 为测试合成
(`caller_repo` 形如 `test_cli_index_then_search_jso0` / `proj` 等 pytest tmp 目录名)。

## 根因

早期写侧缺红线, pytest 跑用例时把埋点直接写进了真实 `traces/` 账本。写侧已修
(`src/kb/trace.py` 的 `trace_enabled`: 测试进程只准写 pytest 临时目录; 实测跑 19 条
`test_cli` 后真实账本 0 字节增长), 但**历史污染是 git 版本化的既成事实**:

- 账本 append-only 且每日定时提交, 改写/删除历史事件 = 伪造观测数据, 后续任何口径
  对账都失去基准;
- 污染只发生在历史区, 新数据干净, 所以"看起来指标变好了"却无人改动逻辑。

## 解决方案

**读侧剔噪, 不动账本**, 并把"剔了多少、剔的谁"如实回传前端(改口径 ≠ 抹事件):

1. `stats.denoise(searches, gets)`: 按 **caller 级**判定(不是事件级), 两条判据任一命中
   即整个 caller 剔:
   - caller 名匹配 pytest tmp_path 形态 `^test_.+_\d\d?$`;
   - 该 caller **全部** search 的 `max(layers.scanned) <= 2`(合成夹具只有 1-2 条条目)。
   用"全部"而非"存在": 真实仓只要长过一次就永不误剔(防误伤是判据的核心约束)。
2. serve 统一读侧入口 `_read()`, 全部数据口(stats/feed/callers/trend/export)走同一函数;
   `?raw=1` 为 URL 级逃生门(自查判据有没有误伤), 缓存键须含 raw(见关联条目)。
3. `/api/stats` 回 `synthetic_count` / `synthetic_total` / `synthetic_callers`, 面板
   `synNote` 明示"本口径已剔除 N 条(caller: ...)"。**计数必须与同屏 KPI 同口径**
   (同 caller + 同窗口的事件数之差), 直接给全账本数会被对账质疑(实测标注 157 vs
   两态 KPI 差 70 遭走查质疑)。

## 验证

- 剔噪前后对比(离线探针): 榜首由合成夹具变回真实条目(`kb-20261013-3069` 21 次),
  零命中榜首变"连接池 耗尽"。
- `Agent-KB` 仓 `tests/test_stats_serve.py`: `test_synthetic_callers_rules`(含防误伤
  用例: `newrepo` 长过一次不剔)、`test_denoise_drops_both_kinds_and_counts`(search/get
  同批剔 + 幂等)、`test_serve_stats_reports_dropped_synthetic`(窗口口径对账 + raw=1 对照)。
- 浏览器回归: 默认口径标注 N=157 且 `/api/feed` 两口径 `X-Total-Count` 差恰为 157
  (956 vs 1113), 数字互相可对账。

## 适用边界与反例

- 适用于"账本/日志已版本化、写侧缺陷已修但历史脏数据仍在"的观测系统。通用做法是读侧
  加口径 + 前端如实标注, 而不是清洗历史。
- 判据不可照搬: `scanned<=2` 依赖"合成夹具条目极少"这一本地事实; 若某真实小库长期只有
  1-2 条条目, 会被误判为合成——需改用更强的 caller 身份判据(如显式 `source=test` 字段)。
- 反例: 若账本尚未进版本控制、且污染区可明确界定, 直接一次性归档隔离更干净, 不必长期
  背读侧判据。
