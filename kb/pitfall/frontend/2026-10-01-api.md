# 分页 API 上叠客户端过滤 = 静默吞数据：不传参默认只回第一页，页外数据整段消失且无任何"还有更多"提示

## 背景 / 现象

FS016 方案实有 30 条任务（DB `GROUP BY app_id` 坐实），方案任务 tab 只显示 20 条，最旧的 10 条整段不见；页面既无分页控件也无空态提示，肉眼完全看不出被截断。

## 根因

`fetchAppTasks` 调 `getTasks()` **不带任何参数** → 后端 `list_tasks` 默认 `pageSize=20` 只回全局（非本方案）最新一页 → 前端再对这一页做 `rows.filter(t => t.app_id === appId)` 客户端过滤。三层叠加：① 后端本就支持 `app_id` 精确筛选参数却没用；② 默认分页 20 条被当成全量；③ 全局列表里混入的 demo 任务还进一步挤占名额。数据量小时（<20 条）该写法"恰好正确"，是典型的**规模依赖型缺陷**——走查必须在数据量超过一页的场景下测。

## 解决方案

- 修复：`getTasks({ app_id: route.params.id, pageNum: 1, pageSize: 100 })`，筛选交给后端，前端不再 filter。复验：tab 行数 20→30，请求串 `?app_id=FS016&pageNum=1&pageSize=100`。

- 判据 1：**凡是「拉列表 → 前端 filter 子集」的代码，必查被拉接口是否分页**。接口分页而调用不带全量/筛选参数 = 缺陷，与当前数据量无关。

- 判据 2：走查列表类页面先 `SELECT COUNT(*) GROUP BY <筛选键>` 拿真值，与 UI 行数对账；只看"页面有渲染"发现不了截断。

- 判据 3：同类需求优先用后端已有的精确筛选参数（此处 `app_id` 在 `list_tasks` docstring 里写明支持），而非拉大页再本地过滤——pageSize=100 也只是把炸弹推远。

## 验证

判据实测：FS016 方案实有 30 条任务（DB `GROUP BY app_id` 坐实），方案任务 tab 只显示 20 条，最旧的 10 条整段不见；页面既无分页控件也无空态提示，肉眼完全看不出被截断。
