# 首帧鉴权票据交换未完成就并发探测健康接口，抢跑拿 401 使派生就绪态停在假阴性

## 背景 / 现象

观测面板 `kb serve` 用"一次性 ticket 换 HttpOnly 会话 cookie"鉴权：带 `?token=` 打开时，
前端先用 `GET /api/session?ticket=…` 换 cookie，再 `replaceState` 把 token 从地址栏洗掉，
之后所有数据请求靠 cookie。首帧还并行发一个 `GET /api/health` 探测 spider 桥是否就绪
（`spiderReady`），据此决定点条目时弹整页 iframe 回放还是内置 SVG 降级版。

实测（2026-11-11，带 `?token=` 全新会话首帧）：**首次**点回放条目弹出内置 SVG 降级版，
刷新一次就正常——像"spider 桥坏了"，但 `/api/health` 单独请求恒返回 `spider_ready:true`。
网络日志显示首帧 `GET /api/health → 401` 早于 `GET /api/session?ticket=… → 200`。

## 根因

鉴权引导（ticket→cookie 交换）是**异步副作用**，而 health 探测 IIFE 与交换 IIFE 被
**并发**发出。health 抢跑时 cookie 还没种上 → 401 → 走 `catch → conn(false)`，而
`spiderReady` 的判定只在"200 且未就绪"的 else 分支里做，401 分支根本不碰它 →
`spiderReady` 停留在初始 `false`，且**启动期只读一次**，交换完成后无人重算。

三个可复用的坑叠加：
1. 依赖鉴权态的启动期消费者没等同一个引导 Promise，形成启动竞态；
2. `catch` 把鉴权失败咽掉，派生状态留在初始值——"看起来正常其实是假阴性"；
3. 启动期一次性读取的派生状态（`spiderReady`）没有失效/重算通道，只能靠刷新自愈，
   于是问题表现为"偶发、刷新即好"，极易误诊成下游服务故障。

## 解决方案

把交换提成**共享 Promise**，所有依赖鉴权态的启动期消费者统一 `await` 它：

```js
const sessionReady = (async () => {
  if (tk0) { try { await fetch('/api/session?ticket=' + encodeURIComponent(tk0)); } catch (e) {} }
})();
(async () => {
  await sessionReady;                        // 探测必须在鉴权态就绪后
  const d = await (await fetch(apiUrl('/api/health'))).json();
  spiderReady = !!d.spider_ready;
  ...
  sessionReady.then(render);                 // 数据请求同批串行, 不再各自并发
})();
```

要点：(a) 用**单个共享 Promise** 让多消费者 await，不是布尔标志、也不是各自 `await` 一个
新建 Promise；(b) 别用 `setTimeout` 重试或轮询"绕过"竞态——等待引导 Promise 才是根因级修法；
(c) 鉴权失败分支要显式区分"确认未就绪"与"未知"，别让 401 静默落成 `false` 假阴性。

## 验证

同机浏览器自动化，before/after 各跑一次全新会话（先探测 `/api/health` 拿 401 证明无残留 cookie）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 首帧顺序 | health 抢跑 → **401**，晚于 session 交换 | `/api/session` → 200，`/api/health` 晚 65ms → **200** |
| `spiderReady` | 停留 `false` | `true` |
| 首次点回放 | 内置 SVG（`#modal` 打开） | 整页 iframe（`#rp.open`，src 含 `?session=`），`#modal` 恒 `display:none` |

## 适用边界与反例

- 任何"一次性票据/授权码换 cookie 或 token"的页面（SSR 引导、OAuth 回调后跳回、
  预览链接换会话）都有这个窗口，与被换的是 cookie 还是 localStorage token 无关。
- 纯 `Authorization: Bearer` 常驻头方案无此问题（没有交换步骤，也就没有窗口）。
- 把 health 挪到 `render` 之后再发同样能消竞态，但把无关探测串行到渲染链上；
  共享 Promise 是代价更小的修法。
- 若消费者在运行期还会反复读该派生态（如轮询），仍需保留重算通道——本修法只保证
  **首帧**读到正确值，不替代"过期后重判"。
