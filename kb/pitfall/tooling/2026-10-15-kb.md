# 多词检索词被整串匹配静默判零命中(kb 检索不分词)

## 背景 / 现象

2026-10-15 观测 agent(flysee 两仓)经 MCP `kb_search` 的真实调用时发现: 自然习惯的
多词查询几乎必然零命中, 且**不报错、不降级、无任何提示**:

| query | 结果 |
| --- | --- |
| `license 授权` | 0 命中 |
| `license` | 10 命中(同仓同刻) |
| `401 登录` | 0 命中 |
| `401` | 10 命中 |
| `推流 fps` / `redis 端口` | 0 命中 |

agent 因此常得出"知识库没有相关知识"的错误结论, 实际库里明明有。

## 根因

`src/kb/search.py` 的 `_hit()` 把条目的 `title tags summary` 三段空格拼成一个
hay, 然后用 `hay.find(q)` 做**整串子串匹配**——没有分词, 没有词间 OR。
多词 query 只有以**完全相同的连续字面形式**出现在拼接文本里才命中:
中文短语如"license 授权"在真实标题/摘要中几乎不会连续共现, 于是静默全灭。
附带效应: 拼接符本身也是匹配面——跨字段边界的"标题尾词+摘要首词"可能意外连成命中。

## 解决方案

**已根治(2026-10-15, commit 0b4a30e)**: `search._hit` 改为按空白分词后逐 token
**AND 匹配**(每个词都须出现, 不要求连续), 并合并各 token 的 hit_spans。多词查询
不再静默零命中。语义要点:

- query `"license 授权"` 现命中**同时**含两词的条目; 缺任一词则该条不命中。
- 空白(含全角空格外的常规空白)是分词符; 纯空白 query 视同无 query(全通过)。
- 想扩召回用单 token; 想收窄叠加 `--type/--domain/--confidence` 过滤器(AND)。

> 注: 采 AND 而非 OR——OR 会被"端口/配置"等泛词污染 agent 检索结果。需要"任一
> 词命中"的场景, 分多次单 token 检索即可。

历史姿势(仍适用于未升级的旧版):

1. **一个检索词只放一个核心 token**; 收窄用过滤器而非往 query 堆词。
2. `kb trace list --zero-hit` 定期抓"agent 问了但没答上"的缺口。

## 验证

```powershell
kb search --query "license 授权" --repo <业务仓>\docs   # []
kb search --query "license" --repo <业务仓>\docs        # 10 条
kb trace list --zero-hit                                # 前者留有零命中记录
```

一手数据: 当日 trace `t-20261015-3ca0`(`license 授权`, 0 命中) 与
`license` 检索 10 命中形成对照; trace 的 `rejected.query` 字段可直接量化"死于
整串匹配"的条数。

## 新发现(2026-10-15): 中文连写词仍需字面完整命中

分词修复只把**空白**当分词符; 中文习惯连写不打空格, `推流死锁` 这类连写串仍是
单 token 走整串 `find`——两词各自在库, 连写照样零命中, 除非库内原文恰有该连写:

| query | 结果 |
| --- | --- |
| `推流` | 6 命中 |
| `死锁` | 1 命中 |
| `推流死锁`(连写) | **0 命中**(两词各自都在库) |

**检索姿势**: 中文查询挑一个最可能被**原样写出**的短词(2–4 字)做单 token 检索,
不要把多个概念拼成长连写串; 需要收窄就分多次单 token 检索后人工取交集。
根治需引入轻量中文分词(2-gram/jieba), 属检索语义变更(索引体积、`hit_spans`
语义连带), 须先写 spec 再动。

## 适用边界与反例

- 单 token 查询(含中英混合单标识符如 `fsync`、`401`)不受影响。
- 英文多词若恰为库内原文短语(如 title 本身含 "access log")则正常命中——
  风险集中在"人/agent 自由组合的多词", 而非语言本身。
- 过滤器参数(`--type` 等)是 AND 收窄, 与 query 多词无关, 不受本坑影响。
